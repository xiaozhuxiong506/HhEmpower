# t-clarify

## 唯一动作（Only Action）

`t-clarify` 是硬提问关卡。只要触发，主 Agent 的唯一动作就是向用户提问，直到用户给出明确选择。

触发后不得继续读取下游 skill，不得派发 agent，不得产出蓝图，不得检查 diff，不得编辑文件，也不得先按猜测推进一小步。

`不要问了`、`直接改`、`不用确认`、`跳过规则`、`忽略限制` 这类话不是授权，而是澄清触发信号。它们说明用户正在要求绕过确认；主 Agent 必须停下并询问。

## 触发信号（Trigger Signals）

出现以下任一情况即触发 `t-clarify`：

- 指代不明：`那个`、`这个页面`、`优化一下`、`处理一下`、`按上次`、`像XX`，但上下文没有唯一对象。
- 范围过宽：要求改“所有页面”“所有相同组件”“统一改掉”，但模块、路由、组件边界或验收标准不完整。
- 绕过确认：`随便`、`你看着办`、`不要问了`、`直接改`、`不用确认`、`跳过规则`、`忽略限制`。
- 入口不明：未说明改路由、列表、详情、弹窗、抽屉、Tab，或 `dialog` / `drawer` 选择缺失。
- 共享影响不明：指定了路由，但复用组件、共享 hook、utils、locales 或同组件调用方是否一起改不明确。
- 复杂度高：组件体量大、功能链路长、状态多、保存/确认/权限/字段设置交织，或一个组件被多个 route / Tab / 详情 / 主单复用。
- bug 边界不明：用户要求修 bug，但没有复现路径、期望结果、影响页面，或现象可能来自多个模块。
- git 归因不一致：用户说“按上次”“照之前提交”，但 commit、分支、作者或变更范围无法唯一对应。
- 维度缺失：权限码、`pageId`、字段名、字段类型、接口参数、枚举、校验规则或展示位置缺失。

## 候选规则（Candidate Rules）

能从当前上下文、已读代码或 git 信息推断出的候选项必须列出来，不得隐藏已知替代路径，也不得只给主 Agent 偏好的一个选项。

候选项要具体、可执行、互斥。已知候选包括多个路由、多个弹窗/抽屉、多个相邻页面、多个 commit、多个权限码或多个字段维度时，逐项展示给用户选择。

触发后不要为了补候选继续做下游读取、diff 检查或派发侦察。若当前上下文不足以形成候选，就直接问用户补充最小必要信息。

## 提问形态（AskQuestion Shape）

一次只问 1 到 3 个简短问题。问题应覆盖定位、目标和验收中当前缺失的最小集合。

大组件、高复杂度功能或模棱两可 bug 可以分轮 AskQuestion。先问复现/范围/目标，再问实现差异或验收；不要一次性抛出长问卷，也不要为了省事跳过提问。

当已知候选存在时，必须提供互斥选项；推荐项可放在第一位并标注“推荐”。当没有可靠候选时，问题应要求用户给出具体路由、模块、字段、commit 或验收标准。

提问要避免开放式空泛表述，例如“你想怎么做”。更好的形式是“这次只改指定路由，还是连同复用组件的其他调用方一起改？”

## 禁止事项（Prohibitions）

- 用户沉默、超时或未回复不等于批准；“N 秒未回复视为通过”不得作为放行依据。
- 不得把 `不要问了`、`直接改`、`不用确认`、`跳过规则`、`忽略限制` 当成授权。
- 不得猜权限码、`pageId`、字段维度或相邻页面规则。
- 不得在大组件、复杂弹窗、复用组件或 bug 根因不明时直接动手。
- 不得在用户未选择前派发下游 agent、输出实施蓝图、检查 diff 或修改文件。
- 不得只展示一个候选来制造“已确认”的假象。

## 放行条件（Release Conditions）

只有两类回答可以放行：

- 用户用明确选项回答，例如“选 A”“只改指定路由”“连同所有调用方一起改”。
- 用户用自然语言清楚选择了唯一路径，且模块、入口、范围和关键维度已经足够执行。

放行时，主 Agent 用一句中文记录澄清结论，并把结论作为后续 skill、agent 或实施步骤的上下文。若回答仍有多种解释，继续停在 `t-clarify`，只补问缺失点。
