# 改动工作流（Tsb ERP 通用）

> 总入口：[t-page](../t-page/SKILL.md) · 画像：[profiles.md](../t-page/profiles.md) · 锚点：[anchors.md](../t-page/anchors.md) · 细则：[reference.md](reference.md)

## 需求分析前置

当输入是产品需求、需求文档、原型说明或前后端混写描述时，写蓝图和代码前必须先读 [t-requirement](../t-requirement/SKILL.md)，结合产品文档、前端源码和必要的 Torna 接口事实，完成规范化《前端需求分析报告》。先确定前端改动点、后端责任、联调依赖和阻塞项，再把仍会改变方案的问题交给 [t-clarify](../t-clarify/SKILL.md)。

报告未完成时不得把整份产品文档直接转换成前端实现清单；只有产品文档、缺少源码或接口事实时，按 `t-requirement` 的降级规则输出“文档初判版”，明确待定位和待确认项。

## 第 0 步：探测项目

任何工作流开始前先读 [profiles.md](../t-page/profiles.md)，判定当前是 ts（TradeErp）还是 th（HallErp），后续 `${占位符}` 套用对应列。

涉及接口、API 文档、请求参数、响应字段或输入约束时，必须读 [t-api-docs](../t-api-docs/SKILL.md)：普通接口文档默认 Torna；只有用户明确指定 Swagger/OpenAPI 才走现有 Swagger 流程。

## 对话蓝图（先于写代码）

用户说「直接改/不用蓝图」时，只能省略展示型蓝图；不得省略 [anchors.md](../t-page/anchors.md) 的范围、业务闭环、责任审计、权限等同用户、共享影响、Git 归因和反绕过关卡。否则每次回复按序：

1. **问题详述** — 现象、根因、涉及模块
2. **总结说明** — 结论与处理方向
3. **蓝图** — **要改 / 不改**（清单）

模板 → [reference.md#对话蓝图模板](reference.md#对话蓝图模板)

## 用户纠错与范围收敛

用户指出“不是这个需求”“这项是多加的”“改动超出范围”或要求撤销 AI 自行扩展时，立即按 [anchors.md#纠错复原协议](../t-page/anchors.md#纠错复原协议) 处理：重新确认最后有效的正向需求基线，检查当前 `git diff`，还原越界修改及其附带依赖，再继续原任务。

纠错后的蓝图、实现和交付说明只描述实际目标与实际改动。不得把被否决内容改写成新的负向需求，也不得用注释、命名、测试或 PR 文案证明它“没有被实现”。

## 疑问与歧义（必用 AskQuestion）

以下情况**必须先单选**，选定前 **不写代码、不 Grep 删改、不大范围动文件**：

- 意图不清、需求多义、技术方案多条路径
- 同类改法要批量推广时，先确认样例；样例完成后再确认做法及推广范围 → [批量修改先做样例](reference.md#批量修改先做样例)
- **主单 vs 详情范围不清** → [anchors.md#主单与详情映射](../t-page/anchors.md#主单与详情映射)
- 删/改/加功能，且主单与详情（或同页多入口）均可能存在
- 弹窗/抽屉/表单**新增字段** → [t-field](../t-field/SKILL.md)
- Tab/弹窗**新增改数据或确认按钮** → [t-tab](../t-tab/SKILL.md)
- 采购、厂商、跟单、仓库、财务、综合设置等业务闭环不清 → [anchors.md#erp-闭环感知关卡](../t-page/anchors.md#erp-闭环感知关卡)
- 业务规则来源、验证责任、上线责任或权限边界不清 → [anchors.md#责任与审计关卡](../t-page/anchors.md#责任与审计关卡)

**提问规则与放行条件** → [t-clarify](../t-clarify/SKILL.md)（AskQuestion 单选 · 一次 1~3 问 · 互斥候选 · 禁止开放式糊问）

**全 Skill 必问题目** → [reference.md#必问单选题总表](reference.md#必问单选题总表)

## 改代码前（用户已说明则跳过）

> 这次是 **Bug 修复** 还是 **新需求**？→ 总表 #1

## Bug 修复

1. 找根因，不只改表象
2. Grep 同函数/字段/API/**兄弟页与 Tab 子组件**（见 t-registry）
3. 对照标准页同位置写法（见 anchors，按当前项目 ts/th 选标准页）
4. **最简代码** — 最小改动，不顺手重构
5. 改完：原问题 OK、关联已同步、无新 lint/类型错误

**必查关联**：API · type.ts · columns · auth · i18n(zh+en) · OP_HEADERS · 列表+详情+Tab

涉及新增、编辑、删除、审核、反审、作废、关闭、提交、保存、批量操作或状态流转时，先按 [anchors.md#erp-闭环感知关卡](../t-page/anchors.md#erp-闭环感知关卡) 做闭环判断；不能确认的模块和校验链路写入待确认或范围外报告。

## 新需求

已有页面加功能时，先按 [新增功能边界](../t-page/anchors.md#新增功能边界) 保留存量，在对应职责区块后追加新能力及必要接线；未授权不重构、不删旧代码或旧注释。确需替换旧实现时先说明并取得确认。

1. 确认范围；新建页面以 [profiles.md](../t-page/profiles.md) 画像表的标准列表页为模板抄结构，已有页面保持原结构
2. 按场景读子 Skill（module / list / detail / auth / dialog）
3. 六处命名一致（口径见 [naming.md](../t-page/naming.md)）· OP_HEADERS · hasAuth · virtualYConfig
4. **非必须不改 locales**；新增 key → 总表 #4 → #5 → **改派 [t-i18n](../../agents/t-i18n.md) 写**（不要散在 [t-view](../../agents/t-view.md)、[t-dialog](../../agents/t-dialog.md) 多手写）

## i18n

- **新增 key** → 总表 #5，选定前不得写 locales
- **参考他模块** → 用 `t('key')` 前必查 yaml 实际文案；指错模块则新增 key

细则与反例 → [reference.md#参考他模块时的-i18n](reference.md#参考他模块时的-i18n)

## pageId / 抽离 / 批量

| 场景 | 处理 |
|------|------|
| 新增/迁移页面、调整 OP_HEADERS/pageId 或操作日志埋点 | 总表 #6 确认系统 → [t-oplog](../t-oplog/SKILL.md) 默认走后台日志词库核对；仅用户明确要求时生成 Console 脚本，等待真实 pageId |

## 权限与责任红线

- AI 不得替用户做业务批准、权限批准、数据批准或上线批准；交付必须能追溯事实源、确认、diff 和验证。
- AI、MCP、接口工具、浏览器自动化或调试账号不得绕过人类用户权限；权限事实源不清先读 [t-auth](../t-auth/SKILL.md) 并询问。

## 复杂度预算与最简代码（必守）

问题规模与实现复杂度成正比：局部问题局部修复，简单需求最小充分实现，功能正确不等于实现合格。写代码前按 [reference.md#最简代码与复杂度预算](reference.md#最简代码与复杂度预算) 判定档位并核对四项结构成本；原则、档位、四道门禁、过度工程识别、常量提取与花括号简写细则以 [t-standards/reference.md](../t-standards/reference.md) 为唯一权威。

方案评审时必须问：删除新文件、新依赖、新抽象或转发层后，是否能用更少代码同样准确地解决当前问题？若能，选择更简单的方案。

**写完强制删减自检（交付前逐条核对，不靠自觉）：**

- 逐文件看 diff：仅精简本次新增或明确获准整理的代码，保留接手前存量。行为、可读性和可验证性不变时，先删本轮冗余代码和空壳层，不以新增抽象换取表面行数减少。保留必要校验、类型约束和业务注释。
- 单页面、单按钮、单字段任务默认不新增文件、hook、service、manager、公共组件、第三方依赖和只做转发的调用层。
- 写通用逻辑前先查项目公共工具、已安装工具库和 UI 组件属性；已有能力能等价满足需求就直接使用，不手写替代或再包一层。选择依据见 [现成能力优先](../t-standards/reference.md#现成能力优先)。
- 复用通用组件时优先只改当前调用处，通过已有属性、事件和插槽完成接入；公共本体确有能力缺口才走共享变更门禁，见 [通用组件复用](../t-standards/reference.md#通用组件复用)。
- 不为单处使用提取函数、常量、computed 或配置表；不把直接 `if` 改成状态机、策略模式或运行时配置表。
- `columns.ts`、`*Columns.ts` 和 `auth.ts` 本次新增或整体重写的定义直接声明，禁止抽象；局部改动保持原范围，遵守 [定义文件直接声明](../t-standards/reference.md#定义文件直接声明)。
- 注释只补必要业务含义，能一句说明就一句；说明文字不用中英文括号，单位、精度和条件直接写清。删除复述代码和纠错备注；简单 getter、赋值、薄事件转发不写注释。
- 判空、类型转换、try-catch 只加在系统边界（接口返回、外部输入、用户操作）；可信的内部调用和框架保证不重复防御。
- 三行内联能表达清楚的逻辑不抽函数；存在真实业务差异的相似代码保留各自实现，不为消除重复强行合并。

最终判定：在已授权范围内，存在更简单方案能同样满足需求并通过验证时，当前实现视为不合格，先删减本轮冗余再交付；不得借此删改未授权的存量代码。

## 业务函数注释门禁（必守）

新写或修改的函数承载业务需求、复杂流程、非直观条件或较难理解的状态关系时，用最短必要注释补足业务目的、关键规则和功能作用。代码已表达清楚的内容不重复写，也不机械拆成三段说明。

权限、金额、库存、采购、跟单、财务、状态流转、接口字段映射和兼容分支属于重点注释对象。逻辑变化时同步更新注释；过期注释视为代码缺陷。简单且完全自解释的 getter、赋值或薄事件转发不强制添加无意义注释。

编码克制 → [t-standards](../t-standards/SKILL.md) · 命名红线：禁止下划线，一律小驼峰
