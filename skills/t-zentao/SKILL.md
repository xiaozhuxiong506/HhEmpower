# t-zentao

## 唯一入口与登录边界

收集“指派给我”的工作项必须先调用 `zentao_collect_assigned_work_items`。同一次工作流只调用一次统一采集；Task、Bug、不同模块和并行执行者都复用该结果。模块执行者不得重新采集、不得重新登录禅道。底层会按同一浏览器 profile 串行化操作并复用一个登录会话。

首次登录或会话失效时，让用户在打开的浏览器中完成登录，然后重试同一个统一采集工具。未登录、采集失败或缺少原文时，不得伪造工作项、分组或完成状态。

工具参数固定以 `pageSize: 2000` 采集当前用户的 Task 和 Bug。原始 ID、URL、标题、正文、描述、备注、日志、项目、产品、创建者、处理人、截止日期、状态、优先级和严重程度是事实源；摘要不能替代原文。

## 场景、系统与模块分析

先判定工作项场景，再定位代码：

- 禅道 Task 标记为 `[禅道需求]`；本流程中的“需求”指指派给我的 Task，不把 Story 混入。
- 禅道 Bug 标记为 `[禅道Bug]`。
- 项目或产品以 `TSBERP` 开头时归为贸易系统。
- 项目或产品以 `HALLERP` 开头时归为展厅系统。
- 项目与产品结论冲突、或都无法识别时，系统标记为“待确认”，不得猜测。

根据原文和仓库代码定位代码模块、关联菜单、组件、接口及精确文件位置。相同系统、相同代码模块的不同工单放在一组。模块无法唯一判断时使用 `zentao_analyze_work_items` 保留“待确认项”，再询问用户。

若 A、B 两个模块共用一个共享组件，必须明确展示共享组件和所有消费者，并询问用户“两个模块都改，还是只改其中一个模块并做差异化处理”。用户确认前不得修改共享组件或派发实现。

进入代码实现前，执行者从 [t-page](../t-page/SKILL.md) 开始，并继承 [t-page/anchors.md](../t-page/anchors.md) 的业务闭环、责任审计、权限等同用户、共享影响和反绕过关卡。

## 标准输出

先提醒用户当前分支。不要固定输出仓库路径、HEAD、工作区状态、文件级 Git 最近修改者；仅在异常或用户追问时补充相关信息。

按“系统 -> 代码模块”分组，先给 Task/Bug 数量摘要，再为每组输出标准 Markdown 表格。列顺序固定为：

| 场景 | 所属项目 | 所属产品 | ID/链接 | 标题 | 创建者 | 当前处理人 | 截止日期 | 代码模块 | 共享影响 | 待确认项 | 详细处理方案与对应位置 |
|---|---|---|---|---|---|---|---|---|---|---|---|

最后一列必须写可执行方案：问题判断、关联模块/组件、精确代码位置、拟改内容和验证方法。尚未完成代码分析时写“待分析”，不得编造位置。

## Task 排期

排期仅允许 Task，禁止把 Bug 纳入排期。先按代码模块汇总 Task，让用户为各模块给出“后天/大后天”等相对日期或 `YYYY-MM-DD` 具体日期；相对日期统一按 `Asia/Shanghai` 转换为绝对日期。

用户已明确每个模块日期及每项工时后，直接调用 `zentao_schedule_tasks`，不再追加第二次确认。每项工时只能为 `1h` 或 `2h`。工具按精确 Task ID 勾选，页面条数设为 2000，进入左下角“编辑”，只把状态设置为进行中，并把截止日期、预计、消耗、剩余设置为用户指定的日期和对应 1h/2h。信息不完整时禁止批量操作。

## 实现完成与 Bug 解决

实现后输出结构化结论，逐项列出 ID、场景、代码模块、完成状态、验证状态、修改位置、验证结果和遗留风险。只有 `completed=true` 且 `verified=true` 的 Bug 才可进入解决候选。

汇总完成且验证通过的候选后，询问一次用户是否解决这些 Bug；未确认时禁止批量解决。用户确认后直接调用 `zentao_resolve_bugs`，无需第二次确认。操作链路固定为打开 Bug -> 点击“解决” -> 解决版本选择“主干” -> 解决日期填写执行时 `Asia/Shanghai` 当前时间前 30 分钟 -> 提交并核验已解决。其他字段一律不改。

Task 不执行 Bug 的解决链路；本流程不自动执行“关闭”。

## 禁止事项

- 不得在模块并发时启动多个禅道登录或重复采集。
- 不得将 Story 当作本流程的 Task，也不得将 Bug 纳入排期。
- 不得在共享组件影响范围未确认时开始修改。
- 不得在排期信息不完整、或 Bug 解决未获用户确认时执行批量操作。
- 不得发明项目、产品、创建者、截止日期、模块、处理方案或完成/验证结论。
- 不得只派发压缩摘要；派发载荷必须保留工作项 ID、URL 和实现所需原文。
