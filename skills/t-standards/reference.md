# TSB 规范参考

项目画像、标准页和 ts/th 差异先读 [../t-page/profiles.md](../t-page/profiles.md)；全局红线读 [../t-page/anchors.md](../t-page/anchors.md)；命名细则读 [../t-page/naming.md](../t-page/naming.md)。

仅新增功能时，按 [新增功能边界](../t-page/anchors.md#新增功能边界) 保留存量。本规范的精简、注释整理和结构优化只约束本次新增或明确获准整理的部分，旧代码质量问题不构成删改授权。

## 命名

- 新页以当前项目标准页为模板，不从另一个项目照搬。
- 路由 path、route name、`defineOptions.name`、目录名、API/type、i18n、auth/log/pageId 命名必须成组替换。
- 禁止业务字段使用下划线命名；后端码、`AUTH_CODES`、`DEFAULT_COLUMNS` 等已有常量名保持原样。
- 函数名前缀优先用 `get`、`handle`、`to`、`open`、`refresh`、`guard`。

### 常量提取与命名

- 只在值有明确业务含义、同一规则真实重复，或直接使用会形成难懂魔法值时提取常量。禁止为了看起来规范而机械地把每个字面量提取成常量。
- 常量名应是当前上下文中最短且无歧义的名称。不重复文件名、模块名、函数名已经表达的上下文，也不用晦涩缩写压缩名称。
- 已有命名空间、枚举或常量对象时，使用命名空间配合简短成员名，例如 `TASK_STATUS.DONE`。不要再写句子式的超长成员名。
- 不设机械的字符上限。评审依据是能否准确理解、是否重复上下文、是否因过长频繁换行，而不是越短越好。

## 主单与详情

- 主单负责列表、查询、工具栏、进入详情入口。
- 详情负责详情头、明细、详情弹窗、详情自己的 OP_HEADERS。
- 详情可以引用主单 auth；主单不得引用详情目录。
- `ts` 常见独立详情目录；`th` 常见内嵌 `Detail.vue`，以 [../t-page/profiles.md](../t-page/profiles.md) 和同模块现有页面为准。

## API

- 新页 API 名照当前项目标准页整体替换业务前缀。
- 列表常见：`GetXxxPage`、`GetXxxColumns`、`UpdateXxxConfig`。
- 详情常见：`GetXxx`、`SearchDetailXxx`、`GetXxxDetailColumns`、`UpdateXxxDetailConfig`。
- 业务 API 第二参若承接日志 headers，形态照当前项目 API 文件，不自行发明包装。

## 接口字段与输入规则契约

接口字段和输入规则是零容忍契约，不允许“差不多”。物料编号、采购编号、客户编码、数量、金额、比例等字段必须以事实源为准，不得按中文含义或相邻页面自行猜字段。

事实源优先级：

1. 用户明确给出的接口字段、值域、长度、规则。
2. 按 [t-api-docs](../t-api-docs/SKILL.md) 获取的接口事实：普通接口文档默认 Torna；用户明确指定时才使用 Swagger/OpenAPI；其次为 MCP schema、后端类型、实际请求/响应样例。
3. 当前模块已验证 API 类型、保存 payload、回显字段和标准页同类实现。

字段匹配规则：

- `columns.field`、表单 `prop`、`type.ts`、请求参数、保存 payload、字段设置 `fieldName` 必须指向同一接口字段。
- `xxxCode`、`xxxNo`、`xxxId`、`xxxKey`、`productCode`、`materialCode` 等相似字段不得互换；若存在多个候选，先问，不猜。
- 只有已有 mapper、接口适配层或后端明确说明时，才允许页面字段名与接口字段不同；必须说明转换位置。
- 接口字段缺失、文案与接口冲突、或 Torna/明确指定的 Swagger/schema 与现有代码冲突时，暂停并让用户确认事实源。

输入规则匹配规则：

- `maxlength` / `minlength`、最小值/最大值、是否允许 0、是否允许负数、整数/小数、小数位、必填、枚举、正则、禁止中文、去空格、粘贴行为必须与事实源完全一致。
- 禁止为了“更保险”自行收紧规则，也禁止为了“体验好”放宽规则；任何偏差都视为未完成。
- 格式化只能影响展示，不得改变提交值语义；金额、数量、日期在保存前必须保持接口要求的类型和精度。
- 复用自定义指令或 utils 前，先确认其行为与事实源一致；不一致时不能直接套用，必须问用户是改公共能力、加参数区分，还是只在指定入口处理。

## 模块解耦

- 页面只引用自己模块、公共组件、公共 hook、明确允许的主单 auth。
- 共享组件/common hook/util 改动前先查调用方，按 [../t-page/anchors.md](../t-page/anchors.md) 的共享影响门禁确认。
- 发现兄弟页也有类似问题时，列入范围外报告，不直接扩散修改。

## 文件职责

| 文件 | 只承载 |
| --- | --- |
| `columns.ts` | 列定义、formatter、列可见性配置 |
| `auth.ts` | `AUTH_CODES` 和后端权限码 |
| `type.ts` | 类型、枚举、页面内数据结构 |
| `index.vue` | 组装、事件、查询、状态流转 |
| `components/` | 弹窗、抽屉、局部子组件 |

禁止把 API、路由、权限判断、日志注册塞进定义文件。

### 定义文件直接声明

- `columns.ts` 和项目约定的 `*Columns.ts` 直接声明列数组、每列字段与属性。禁止抽象列定义，包括列工厂、builder、包装函数、共享默认列对象和配置生成器；同文件内封装也不例外。
- `auth.ts` 直接声明 `AUTH_CODES` 对象，已提供的后端权限码逐项完整写入。来源确认及后续配置流程沿用 [t-auth](../t-auth/SKILL.md)。禁止权限码工厂、前缀拼接、映射生成或中间配置层。
- 这两类定义允许适度重复。多个调用点、其他模块已有模式或抽象后少写几行，都不能作为新增定义抽象的理由。
- 继续复用现成 formatter、`filedMapping`、表格 Hook、`hasAuth` / `v-auth`，详情继续引用列表 `AUTH_CODES`。复用这些能力不等于抽象列或权限码定义。
- 约束本次新增或整体重写的定义，不授权清理范围外历史封装。仅改一个标题或宽度时保持局部修改；历史结构阻碍本次任务时先说明最小影响范围。

## 最小充分实现与四道结构成本门禁

修改需求、修复 Bug 或设计方案时，先给当前问题设置复杂度预算。默认只引入解决当前问题所必需的概念、分支、文件和依赖。

在行为、可读性和可验证性不变的前提下，精简本次新增或明确获准整理的代码。先删这部分中的冗余分支、别名转发和空壳层，再考虑局部简化；不通过新增抽象把代码藏到别处。必要校验、权限边界、类型约束和有价值的业务注释必须保留。

- **复用顺序**：现有能力 → 项目已依赖的框架/库 → 当前职责内的局部实现。
- **最小充分实现**：能够准确满足需求并通过验证的最小方案；不为假设中的未来需求预埋扩展点。
- **抽象门槛**：默认不新增抽象。至少两个已确认调用点存在真实重复、符合项目现有结构且能明显降低整体复杂度时，才考虑提案；按工作流确认后实施。columns / auth 定义始终按上方直接声明规则处理。
- 单个页面、单个按钮、单个字段或单个 Bug 默认不得新建 hook、service、manager、工具库或引入第三方依赖。
- 不用“通用性”“以后可能复用”“顺便统一”为过度封装辩护；需要扩大公共能力时，先走共享影响确认。
- 优先选择容易阅读、测试、删除和回退的实现；避免聪明但隐晦的一行代码，也避免层层转发的空壳封装。

### 新文件门禁

新文件只有在继续写入现有文件会破坏现有文件职责，或项目既有结构明确要求独立文件时才成立。新增前必须指出文件路径、唯一职责、实际调用方，以及为什么当前文件局部实现不合适。把一个短函数搬到新文件、只为“目录更整齐”拆文件，或创建仅被一个位置调用的通用文件，均不算必要。

新页面按项目既有结构要求创建 `columns.ts`、`type.ts`、`auth.ts` 等职责文件属于有效理由；单按钮、单字段、单校验或单 Bug 默认在现有职责中完成。

### 新依赖门禁

新增第三方依赖前必须证明项目现有能力和已安装框架无法安全、清晰地满足需求，并说明包体、维护、安全和锁文件影响，获得用户确认后才能引入。只为一个简单转换、格式化、判断或少量工具函数新增依赖，直接判为过度工程。

### 新抽象门禁

新增 hook、service、manager、工具库、公共组件或通用配置，至少需要两个已确认的实际调用点，并证明抽象后减少的是整体重复、分支或认知成本，而不是把同样逻辑换一个文件存放。只有一个调用点、只有未来设想，或项目没有同类结构时，保留局部实现。满足门槛不等于自动获准，仍须按工作流确认；本门禁不豁免 columns / auth 定义禁止抽象的规则。

### 新层级门禁

每个新增调用层必须拥有明确职责，例如校验契约、状态管理、业务策略、资源生命周期或真实复用；只转发参数和返回值的空壳 wrapper、service、adapter、manager 不得新增。评审时按用户阅读路径计算跳转次数：去掉本次新增中间层后同样清晰正确，就去掉该新增层。

### 过度工程识别

| 常见理由 | 判定 |
|----------|------|
| “以后可能复用” | 没有已确认调用点，不成立。 |
| “结构更清晰” | 只移动代码、不减少分支或职责，不成立。 |
| “职责单一” | 把一个简单流程切成多个空壳文件属于碎片化，不成立。 |
| “最佳实践都这样” | 当前项目没有同类结构且需求不需要，不成立。 |
| “方便测试” | 现有职责内可以直接验证时，不成立。 |

最终验收同时检查功能和结构成本。在已授权范围内，存在更简单方案且能同样满足需求、保持清晰和通过验证时，较重方案视为不合格；应删除本次不必要的新增文件、依赖、抽象和转发层，恢复最小充分实现。

## 语法规范与适度简写

简单、单行、无副作用的 `return`、`continue` 或 `break` 分支允许使用无花括号简写，但必须同时满足以下条件：

- 条件和语句经过项目 formatter 格式化后仍在同一物理行。
- 分支不涉及权限、金额、状态流转、接口参数等关键业务规则。
- 分支不执行赋值、函数调用、异步操作或其他副作用。
- 分支不带 `else` / `else if`，也不需要注释才能说明原因。

格式化后发生换行时必须使用花括号。条件或语句过长、存在副作用、属于关键业务判断、带 `else` / `else if`，或后续很可能追加语句时，也必须使用花括号。不要为了压缩行数写难读的一行代码，也不要把所有简单保护分支机械展开成三行。

```ts
if (!item) return;

if (shouldPersistChanges) {
  await saveChanges();
}
```

解构、属性简写、可选链等常规语法可以使用，前提是不隐藏业务含义，并符合项目 lint 和 formatter 的结果。

## 业务规则函数与状态矩阵

### 决策顺序与适度重复

- 多状态业务函数按业务优先级排列分支，优先使用早返回保持控制流平直。分支顺序决定结果时，注释说明这是一条业务优先级，不随意交换、合并或改成无序映射。
- 两个相似函数存在真实业务差异时，保留各自局部完整的独立实现。局部完整优先于为了表面 DRY 增加跨文件跳转，让维护者能在一个位置读完当前入口的规则。
- 禁止只为消除重复引入状态机、策略模式、配置表、执行器或多层 wrapper。只有抽出的共享规则同时减少代码重复和认知成本，而且不会隐藏两个入口的差异时，才提取小型纯函数。
- 函数只接收完成当前计算所需的最小字段集。不要因为调用方拥有完整实体，就让纯判断依赖整页对象、组件实例或无关字段。
- 纯业务判断优先只依赖入参。store、`localStorage`、`computed`、路由和接口调用属于环境访问；只有文件现有职责本就包含这些能力时才保留在一起，不因本条规则机械拆文件。

### 边界归一化与语义类型

- 外部数据只在系统边界归一化一次。边界可以是已有 API mapper、适配层、query transform 或页面数据入口；进入业务逻辑后按稳定类型直接比较。
- 业务判断中禁止散落 `Number`、`String`、`Boolean` 或 `as` 转换。同一字段一处强转、一处直接比较会产生不同结果，并掩盖接口契约错误。
- 区分传输类型和领域类型。传输类型反映接口真实返回的 `unknown`、字符串或数字，边界完成校验后再得到业务可用的领域类型。
- 优先复用已有 mapper 或适配层；一个局部兼容问题不新增一次性文件、schema 依赖或通用解析体系。确实没有现成边界时，在当前职责的单一入口建立最小归一化函数；转换仍不得进入业务分支。
- 不同业务概念即使数值相同也不得复用彼此的常量，例如页面 Tab 类型不能借用单据类型常量。相同数字不代表相同语义。
- 已使用 `as const` 定义有限值集合时，可以从常量推导字面量联合类型，避免再手写一份可能漂移的宽泛 `number` 类型；只有接口允许未知扩展值时才保留宽类型，并明确处理方式。

### 行为矩阵与一致性

- 工作流、角色、单据类型、状态等多个维度共同决定结果时，先整理行为矩阵。矩阵用于理解和测试，不等于把运行时代码改成动态配置表。
- 每条高优先级规则至少有一个命中用例；存在重叠条件时，增加冲突用例固定优先级。行为零变更重构优先使用重构前输出作为对照，逐组合核验新旧结果。
- 未知状态的默认行为必须明确。按钮和权限规则通常安全失败为不显示或不可操作，但若现有行为或产品规则不同，以事实源为准，不能静默发明。
- 注释、常量、类型和值域术语必须一致。同一角色不能一处叫主管、一处叫管理员；同一状态值不能在常量中叫“驳回”、在字段注释中叫“通过”。
- 返回数组同时表达按钮集合和显示顺序时，测试必须同时检查成员与顺序。

## 业务与复杂函数注释门禁

以下任一条件命中时，函数或关键代码块必须有清晰注释：承载业务需求、包含多状态/多分支、涉及权限或金额、存在非直观兼容逻辑、字段映射难以从代码直接判断，或维护者需要额外上下文才能安全修改。

注释用最短必要说明补足代码读不出的业务目的、关键规则和功能作用，能一句说明就一句，不机械分成三个小节。需要依据才能理解的规则，简要写明事实来源或对应状态值，禁止把推测写成确定规则。

持久化注释只描述当前代码仍然成立的业务事实和设计原因。本轮对话、AI 的错误尝试、用户对该尝试的否决以及已撤销方案不属于业务事实，按 [纠错复原协议](../t-page/anchors.md#纠错复原协议) 清理，不写成“不要 X”“不支持 X”“已移除 X”等反需求注释，也不进入命名、测试或文档。

用户明确确认某项禁令是长期业务、安全或合规规则时，注释应表达稳定的不变量及其事实来源，例如“提交范围仅包含当前订单明细”，而不是记录“不要处理曾经误加的其他订单”。

- 函数级注释解释职责和业务约束；复杂分支前的局部注释解释“为什么进入此分支”。
- 同一业务含义说明一次即可，删除重复修饰和特意排除无关方案的备注。说明文字不用中英文括号，字段含义、单位、精度和条件改为简短直述，例如 `// 金额单位为元`；保留必要业务事实，不为缩短注释删掉关键规则。代码表达式中的语法括号保持原样。
- 权限、金额、库存、采购、跟单、财务、审核/反审/作废/关闭等状态流转必须优先注释业务目的、关键规则和功能作用。
- 禁止把代码逐行翻译成注释，例如“赋值给变量”“遍历数组”“调用接口”；这类注释增加噪声但不提供上下文。
- 简单、自解释、无业务规则的 getter、纯赋值和薄事件转发不强制注释。
- 修改逻辑时同步修改注释；注释与实现冲突、状态值过期或规则来源失效，按代码缺陷处理。

## 现成能力优先

写通用逻辑前，先查现成能力。能够等价满足需求时直接复用，不手写同类逻辑，也不为一次调用再加工具函数或包装层：

1. **项目现有能力**：先查 `@/utils`、`@/utils/hooks`、`@/hooks`、`@/directives`、当前模块 `hook.ts`、同模块兄弟页。
2. **框架/库能力**：项目没有对应封装时，查已安装的 Vue、Element Plus、VXE、dayjs、lodash-es 等工具库和 UI 库。组件属性、事件和内置方法能完成的交互，直接配置组件。
3. **最小本地实现**：现有能力确有缺口时，仅在当前职责内补足，并说明已查能力及其不足。新增依赖仍须通过新依赖门禁，不因“优先用库”自行安装另一套库。

使用前以当前项目版本的类型、官方文档及现有接线核对用途、输入输出、精度和时区；没有查到 API 时不凭记忆编造。复用已有能力仍须遵守 columns / auth 定义直接声明规则。

必须优先查现成能力的典型场景：

- 防抖、节流、loading guard、重复提交防护。
- 日期格式化、时间范围处理、时区/日期展示。
- 金额格式化、千分位、保留小数、负数展示。
- 表格 formatter、枚举映射、状态色块、空值展示。
- 字符串清洗、空值判断、数字转换。

表格 formatter 优先使用 `utils`、`filedMapping`、同模块 columns 既有 formatter。禁止在每个 columns 里复制一份相同格式化函数。

### 通用组件复用

- 接入前核对组件已有的 props、事件、插槽、公开方法和现有用法；能满足需求时，只在当前调用处做最小配置或接线。
- 不为当前页面的偏好修改公共组件本体或默认值，不复制组件、增加空壳 wrapper，也不顺带调整其他调用方。
- 确有能力缺口时，先按 [共享影响关卡](../t-page/anchors.md#共享影响关卡) 列出调用方、影响范围和最小方案并取得确认，再做兼容扩展；保持已有调用行为，不借机重写组件、重设计接口或批量迁移。

### 日期范围与组件配置

- 日期选择器的默认起止时刻先查组件配置。Element Plus 的 `default-time` 接收 `Date`，用原生 `Date` 提供配置本身属于正常接入；先查常量使用处，不单凭构造语句判定造轮子。详见 [DatePicker 官方示例](https://element-plus.org/en-US/component/date-picker.html#default-time-for-start-date-and-end-date)。
- 需要按实际选择日期计算查询日边界时，优先用项目已有日期工具或已依赖 Day.js 的 [startOf](https://day.js.org/docs/en/manipulate/start-of) / [endOf](https://day.js.org/docs/en/manipulate/end-of)。组件需要原生 `Date` 时使用 [toDate](https://day.js.org/docs/en/display/as-javascript-date)，接口需要字符串时按已确认格式输出。
- 组件配置已经覆盖需求时，不再叠加 watcher、手动补时分秒或重复格式化。替换既有写法须保持时间范围、秒/毫秒精度、时区及回显行为，不机械把所有 `new Date` 换成 Day.js 对象。

## 输入限制与自定义指令

遇到输入框限制时，先查项目是否已有自定义指令或通用工具，再决定写法。

常见限制包括：

- 数字范围：最小值、最大值、非负、正整数。
- 小数位数：金额、数量、比例、折扣。
- 字符限制：禁止中文、只能英文/数字、编码格式。
- 粘贴限制：粘贴时也要生效，不只处理键盘输入。
- IME 输入：中文输入法组合态不能误删或造成光标异常。

处理顺序：

1. 查 `@/directives`、全局 directive 注册、标准页同类 `v-*` 指令。
2. 验证现有指令是否完整覆盖事实源规则：长度、值域、是否允许 0/负数、小数位、必填、输入、粘贴、清空、边界值、中文输入法。
3. 若现有指令准确，直接复用，不再写 `oninput` / 正则清洗。
4. 若现有指令不完整，优先查 `utils` 或表单 validator 是否已有组合方案。
5. 仍无现成能力时，只在当前组件写最小逻辑，并报告“未找到可复用指令/工具”的证据。

禁止为了一个输入框临时复制大段正则、监听器或 formatter。若多个页面需要同一限制，先按共享影响关卡确认是否应补公共指令或公共工具。

## virtualYConfig

vxe-grid 页面默认配置：

```typescript
rowConfig: { keyField: "id", isHover: true },
virtualYConfig: { enabled: true, gt: 10, oSize: 5 }
```

- 必须配合 `:height="tableHeight"` 或弹窗固定 height。
- `gt: 10` 是页面级触发阈值；不要照全局插件默认值覆盖页面标准。
- `virtualXConfig` 一般走全局插件，不在页面单独配置。
- 弹窗/抽屉内 grid 也按同一规则处理。

## 列宽与 minWidth

- 新需求页禁止使用列 `minWidth` 或 `columnConfig.minWidth`。
- 主单/详情明细：业务列少于 9 列时不设业务列 width；9 列及以上才按通用 width 处理。
- 弹窗 grid：业务列少于 7 列时不设业务列 width；7 列及以上才按通用 width 处理。
- 业务列数不含 `seq`、`checkBox`、operation 操作列。

通用 width：`seq` 50、`checkBox` 50（跟踪 60）、图片 80、编号 160、状态/数量 120、金额 120（采购主金额 130）、日期 160、操作 150。

列类型按字段语义智能归类，不按字面死记，也不参考其他页面或凭印象取值：

- 编号类：`field` 含 `code`/`no`/`num`，或中文含义为编号/编码/单号/批号/条码/序列号 → 160。
- 日期类：含日期/时间/创建时间/修改时间/交期/到期 → 160。
- 金额类：含金额/单价/价税/合计/额（语义为钱）→ 120（采购主金额 130）。
- 状态/数量类：状态、数量、件数、行数、比例、百分比 → 120。
- 图片类 → 80；`seq` 50、`checkBox` 50（跟踪 60）、操作列 150。

`width` 只允许取速查表数值。写列前逐列归类取值，交付自检时逐列核对；禁止凭印象、四舍五入或照抄其他页面取相近值（例如编号列写成 150）。归类拿不准时按最接近的业务含义归类并在交付中说明。

搜索项宽度：`productKey` 220px、`codeKey` 160~180px、select 140px。

## columns 属性顺序（Columns Property Order）

普通列按此顺序组织：

```typescript
{
  // 中文注释
  field,
  title: t("..."),
  width,
  className?,
  align: "center",
  sortable: true,
  visible: true,
  type?,
  formatter?,
  fixed: "",
  slots?
}
```

- 金额列：`className: "text-right"`、`align: "right"`、`headerAlign: "center"`、`utils.formatWithCommas`。
- 操作列：`field: "operation"`、`fixed: "right"`、`width: 150`。
- 枚举 formatter 用 `filedMapping`；状态色块用 `type: "html"` + `spanHtml`；日期用 `utils.filterDateTime`。

## select null

值可能是 `null` 的 `el-select` 必须保留空值配置：

```vue
<el-select v-model="form.xxx" :empty-values="[null, undefined]" />
```

如果数值 `0` 是合法选项，先查当前项目标准页同类写法，不自行改变空值语义。
