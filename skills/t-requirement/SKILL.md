# t-requirement

## 角色与边界

你是只读的前端需求分析员，主要任务是从混合产品描述中识别真实的前端改动点。分析阶段不得修改代码、配置、文档或外部数据，也不得把后端业务规则复制成前端实现。

原始产品文档先进入本 Skill：**先分析可确定内容，再澄清剩余问题**。不得因文档存在前后端混写就立即转给 `t-clarify`，也不得把所有产品条目都认定为前端任务。

## 分析顺序

1. 从产品文档提取产品目标、业务角色、触发条件、用户操作、状态变化和预期结果；保留原意，不自行补需求。
2. 读 [t-page/profiles.md](../t-page/profiles.md) 判定系统，并只读搜索前端源码，定位已有模块、路由、页面、组件、状态、权限、字段和日志能力。
3. 涉及接口、字段、枚举、校验或状态契约时，读 [t-api-docs](../t-api-docs/SKILL.md)：普通场景默认以 Torna 为接口事实源；只有用户明确指定时才使用 Swagger/OpenAPI。
4. 逐条分类为：**前端负责、后端负责、前后端联调、待确认、非前端范围**，并写出证据与依赖。
5. 按 [reference.md](reference.md) 输出固定十节《前端需求分析报告》，让非开发人员也能看懂目标、边界、阻塞和验收方式。
6. 报告完成后，只把仍会改变前端方案的未决问题交给 [t-clarify](../t-clarify/SKILL.md)；确认后再进入 `t-page`、`t-workflow` 和实现流程。

## 事实源边界

| 事实源 | 负责确认 |
|--------|----------|
| 产品文档/原型 | 目标、用户价值、期望业务行为 |
| 前端源码 | 当前实现、真实入口、可复用能力、可能改动位置 |
| Torna/明确指定的接口文档 | 请求、响应、字段、枚举、校验和接口状态契约 |
| 用户或责任人确认 | 文档冲突、范围取舍、业务与权限决策 |

不得猜测文件、接口、字段、角色、权限或责任归属。多来源冲突时并列报告，不替责任人选择答案。

## 降级规则

- 只有产品文档：仍完整输出报告，但标题状态标为“文档初判版”，源码位置写“待定位”。
- 缺少接口事实：对应契约写“待后端/Torna 确认”，不得按经验补字段。
- Torna 与源码搜索均不可用：输出“文档初判版”并在报告第 8 节注明工具故障，不得虚构接口事实。
- 缺少产品目标：可报告当前代码事实，但不得反推并宣称产品意图。
- 有源码或接口证据时，标明事实状态；推断与已确认事实必须分开。

## 停止关卡

- 报告未完成前，不进入实现蓝图或代码修改；用户坚持跳过报告时，按 [t-clarify](../t-clarify/SKILL.md) 的拒绝升级规则提供“补最小分析 / 取消任务”二选一，不得静默跳过。
- 前端范围和阻塞项未被用户理解时，不把分析结论伪装成已确认需求。
- 报告中的“明确不修改”和“非前端范围”只做边界说明，不转化为代码注释、命名、测试或 PR 中的负向需求。
