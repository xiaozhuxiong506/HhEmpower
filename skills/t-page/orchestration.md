# 页面按需调度与共用约定

本文件定义两种入口共用的质量与交接要求，以及普通 `/t-page` 的按需分工。角色数量随实际工作变化，适用规范不随之减少。

## 调度模式与任务权限

- 普通 `/t-page` 默认按需。`t-start`、`t-new-module`、`t-review` 继承同一任务的调度模式；没有已选模式时使用按需。自动规则、角色文件或专业 Skill 的加载不会把任务升级成全量。
- `/t-page-max` 或用户明确要求全员参与时，另读 [全量阶段表](../t-page-max/orchestration.md)，使用其 22 角色派发与完整回执要求；不套用下方按需角色选择。转读共用文件不重置模式。
- 开发/修复模式：只实现已确认的需求及必要直接依赖，审查发现的本次缺陷交原负责人修正并复查。
- 只读分析/审查模式：参与者只核查，不复制模板、不注册路由、不改代码。发现问题继续汇总结论，不自动修复；“报告已完成”不等于“代码可交付”。
- 调度模式与读写权限独立。全量不授权全仓扫描、聊天查询或外部写入；独立钉钉/禅道查询及非页面任务直达对应入口。

## 按需模式的需求分析交付

用户只要求前端需求分析报告、未要求实现或审查代码/diff 时，由主 Agent 按 [t-requirement](../t-requirement/SKILL.md) 完成报告、必要事实核查和剩余澄清即可交付。只按实际缺口选择事实/影响分析角色；后续实现的复杂度不决定本轮角色数量。

这种任务以报告完整性和事实来源为验收依据，不进入下方代码任务的实现前取证、t-spec/t-code/t-build 收口或最简代码复核。用户选择全量模式时仍执行全量阶段表，各角色按只读范围核查。

## 代码任务派发前

1. 按 `t-page` 完成需求理解、画像探测和页面任务概览。未解决的范围、事实源、共享影响、权限或字段歧义交 `t-clarify`；已确认的信息直接沿用，不重复索要。澄清阻塞时只读已知事实，不派实现、不写代码。
2. 主 Agent 读取 `t-standards` 及 `reference.md`。涉及列表时加读 `t-list`；专业 Skill 按实际文件、调用关系和需求选择，不靠用户逐个点名。
3. 按下节判断实际工作量，记录需要执行的工作、负责人和前置事实。只为必要角色核对工具与角色文件，不预建全员待办。
4. 支持命名角色时直接派发；仅支持通用子代理时要求其读取获派角色文件。没有子代理能力的简单任务仍可由主 Agent 处理并如实记录；需要独立审查或明确要求委派的工作缺少工具时，报告具体缺口，不伪造回执。

## 按需选择角色

同类改法要批量推广时，先按 [批量修改先做样例](../t-workflow/reference.md#批量修改先做样例) 取得样例许可，只给样例及必要依赖的负责人写权限。样例完成后展示实际改动，等待用户确认做法和推广范围；此前其余位置只读，不因空闲并发名额提前派写入。获准后再向其余位置派发写入，单一功能的多个依赖文件不机械拆成多个样例。

范围明确、现有文件内局部修改、无契约/权限/日志/共享影响、没有复杂业务状态时，由主 Agent 直接取证、修改、自检并运行相关验证，不启动子代理。例如已定位的列宽或局部样式调整；检查与改动相关的现有标准，不展开无关模块。新页面、接口接线、权限/pageId、跨模块影响或多状态业务规则不属于此档。

其他任务按下表匹配所需工作，只派命中的角色。角色不是必填清单，无须让无关角色启动后再声明“不适用”；需要读取一个专业 Skill 也不等于必须创建同名代理。

| 实际工作 | 选择角色 |
| --- | --- |
| 入口、模块或主单/详情边界未定位 | [t-scout](../../agents/t-scout.md) |
| 新页面、结构或行为改动需要标准页与复用取证 | [t-survey](../../agents/t-survey.md) |
| 调用方、兄弟页、共享或业务闭环影响需专项核对 | [t-impact](../../agents/t-impact.md) |
| 任务明确需要钉钉聊天事实 | [t-dingtalk](../../agents/t-dingtalk.md) |
| 多模块任务分工；新建必要骨架 | [t-mod](../../agents/t-mod.md)；[t-scaffold](../../agents/t-scaffold.md)，分别按需 |
| 接口、类型、权限、日志、文案、路由有改动或待核查 | 分别选择 [t-api](../../agents/t-api.md)、[t-type](../../agents/t-type.md)、[t-auth](../../agents/t-auth.md)、[t-oplog](../../agents/t-oplog.md)、[t-i18n](../../agents/t-i18n.md)、[t-route](../../agents/t-route.md) |
| 修改公共组件/Hook/utils 本体 | [t-shared](../../agents/t-shared.md)；只调用既有能力不派此角色 |
| 列、弹窗、页面组装或样式需要专项实现/核查 | 分别选择 [t-col](../../agents/t-col.md)、[t-dialog](../../agents/t-dialog.md)、[t-view](../../agents/t-view.md)、[t-style](../../agents/t-style.md) |
| 页面/路由/Tab 登记发生变化或需要发现核查 | [t-registry](../../agents/t-registry.md) |
| 非简单代码任务的收口 | [t-spec](../../agents/t-spec.md) → [t-code](../../agents/t-code.md) → [t-build](../../agents/t-build.md)；有新增、修改或复用文案时，加 [t-i18n-check](../../agents/t-i18n-check.md) 与 t-spec 同阶段审查 |

主 Agent 按真实依赖排队：范围与标准先确定，API 契约先于类型与接线，骨架先于专业实现，共享本体先交还再迁移调用方，同文件样式等实现者交还后处理。只等待本任务实际需要的前置工作，不为跳过的角色补空阶段。复杂度或影响增加时补充所需角色，不自动升级全量。

已在同一任务收集且仍有效的范围、规范来源和系统证据直接复用。源码、契约或影响范围变化后只补查受影响部分；新建/改动 grid 仍核对完整 Hook 接线，不能以已有结论跳过最终 diff 审查。

## 单一调度与文件归属

以下角色分工适用于实际委派的工作。普通简单任务由主 Agent 作为唯一文件负责人，不因列出职责而补派代理。

- 由主 Agent 统一创建、排队、等待和复用实例。`t-mod`、`t-scaffold` 或其他角色需要下游工作时返回任务与文件清单，不自行再开一套子代理，避免重复派发。各角色收到任务后只执行获派职责，不再次运行整个 `t-page`。
- 每个角色独立读取其角色文件、命中的 Skill 和必要参考，回执列出实际读取项。只读 description、列一个 Skill 名或收到主 Agent 的摘要不等于完成规范读取。
- 每个可写文件在同一时刻只有一个负责人。`index.vue` 由 `t-view` 组装，再交 `t-style`；弹窗内部交 `t-dialog`，父页接线交 `t-view`；`t-col` 只管列定义，不代写页面逻辑。
- 公共组件、Hook、通用 utils 实现由 `t-shared` 单点修改。具有独立职责的登记文件仍归专项角色：API 归 `t-api`、类型归 `t-type`、auth 归 `t-auth`、operationLog 归 `t-oplog`、locales 归 `t-i18n`、路由归 `t-route`。共享属性不豁免用户确认与引用扫描，专项角色与 `t-shared` 不得争写。
- 调用既有公共 Hook 不等于修改 Hook 本体。新增公共层、依赖、文件或跨模块修改仍执行 `anchors.md` 与 `t-standards` 的确认和最小改动要求。
- 子代理不得顺手修改范围外问题。跨模块任务按模块锁定文件，仍禁止脚本批量改 ERP 业务源码。

## 派发输入与角色回执

主 Agent 给每个角色传入以下信息；首次只读核查不授予写权限，实施前再明确可写文件：

```text
角色及角色文件：<名称、当前插件内实际路径>
调度模式：按需 或 全量
任务模式：开发/修复 或 只读分析/审查
阶段与前置结果：<已完成角色回执、尚未解决的阻塞>
用户需求与确认：<正向目标、范围、验收标准；不包含自行扩展>
存量重构或删除授权：<默认无；已授权时写具体范围，不以新增功能或可写文件替代>
批量样例与推广确认：<不涉及，或样例位置、当前做法、用户确认及获准推广清单；待确认部分只读>
系统画像与证据：<已确认系统、业务源码根/路由；沿用本任务结论，不从后台 URL 或共享组件重新猜测>
可读范围 / 可写文件：<明确路径；无写入授权时写“无”>
规范与事实：<标准页、规范参考、接口/权限/字段事实、必要 Skill 路径>
本角色交付：<实现/核查内容与证据；无关时本人核查后说明不适用>
调度边界：只执行本角色；不自行派发其他角色；不扩大外部访问。
```

每个实际实例至少有一条回执，由主 Agent 补入工具返回的真实实例标识。主 Agent 直接承担的取证和检查标记为主 Agent，不填写虚构实例：

涉及日志的 `t-oplog` 派发与回执还须带上 [日志目标与来源核对](../t-oplog/SKILL.md#日志目标与来源核对) 中的系统、后台应用、PC 平台及逐项 pageId 来源。主 Agent 将同一份证据交给 `t-code` 复核；来源缺失或系统冲突时停在日志步骤，不换用其他系统结果。多个角色使用后台时，应用切换与保存不得并发操作同一标签页。

| 角色 / 实例 | 阶段 | 实际读取的规范 | 文件或检查范围 | 证据 | 结果 |
| --- | --- | --- | --- | --- | --- |
| <角色 / 工具返回标识> | <阶段> | <实际读取路径> | <路径或明确无写入> | <代码位置、检查命令及结果或不适用依据> | 通过 / 不适用 / 需修正 / 阻塞 |

“待派发”“执行中”只表示进度，不是完成回执。角色已经派发但尚未返回时不能先记通过。同一角色返工可复用实例，但必须更新其负责的最终文件版本和复查结果。跨模块的多个 `t-mod` 实例分别记录，不代替其他角色。

## 实现前必检证据

主 Agent 或已派发的 `t-survey` 在写入前给出下表中适用项的标准来源，避免重复取证；最终由主 Agent 自检或必需的 `t-code` 独立复核。三个槽位均有结论，不涉及或本次未改动的项以范围/diff 为依据简要说明，不展开无关扫描。全量模式固定由 t-survey 取证、t-code 复核。

| 必检项 | 写入前的标准证据 | 实现与终审证据 |
| --- | --- | --- |
| import | 当前画像标准页的实际 import 组、`t-standards/reference.md` 的 import 顺序、相关 lint 配置 | 本次文件的 import 位置与对照结果；不能拿 legacy 旧页作新页标准 |
| 公共表格 Hook | 实际 Hook 导出/来源、标准页调用、项目列偏好 API 与保存链路 | 列表核查 `useGridPreferences`、`useColWidthSave`、恢复/提交偏好、`resizable-change` 等实际接线，不能只检查两个 import 名称 |
| 现成能力复用 | 本次所需 utils、hooks、directives、fieldMapping/filedMapping 的实际导出与适配依据 | 实际调用位置；没有或不适配时记录搜索范围和理由，不为补表造公共抽象 |

列表基线以 [t-list](../t-list/SKILL.md) 和当前项目标准源码为准；列偏好已有公共 Hook/API 时不能用页面 localStorage 或手写监听替代。非列表组件不强塞列表 Hook，但新建或改动的 grid 仍按命中的规范核对虚拟滚动、height、列宽与字段设置。

标准文件、Hook 导出或事实源找不到时先报告缺口，不能填写猜测路径或复制旧实现冒充取证。其他权限、日志、i18n、字段、Tab 和防御性编程规范由相关角色按实际范围覆盖，以上三项不替代专业检查。

## 审查、返工与验证

普通简单代码任务由主 Agent 对照正向需求、适用规范和最终 diff 自检，运行与风险相称的相关验证；无需独立实例或固定全套构建。非简单代码任务必须派独立 `t-spec → t-code → t-build`，有文案工作时 t-i18n-check 与 t-spec 并行。全量模式使用全量阶段表的固定收口。

第一阶段未通过先修正并复查，再进入代码终审；代码终审未通过先回原实现者，不能用 build 抵消审查结论。只读任务只汇总失败项，不进入返工。

- `t-spec` 对照需求、范围、规范取证与 diff；需要文案审查时由 `t-i18n-check` 对照实际文案；`t-code` 给出上述三个必检槽位及相关专业项的结论。
- 违反本次适用规范的 Critical 或 Warning 都需要修正，不能因严重级别较低自动放行；一般建议与范围外既有问题只报告，不擅自扩大改动。用户明确接受某项偏离时记录具体项与影响，交付不得标“规范全部通过”。
- 修正后把实际 diff 交原审查者复查；改动影响前一阶段结论时使其失效并补查。运行验证之后又修改源码，旧验证不能覆盖新版本，重新执行受影响的审查和验证。
- `t-build` 先检查包管理器、项目脚本和副作用，再运行既有类型检查、仅本次文件的 lint、开发交付所需构建和相关烟测。不得使用 `--fix`、运行发布脚本、修改依赖，或用浏览器操作生产写接口。只读任务遵守用户限制，不能安全执行的检查明确记“未运行”。
- 每个验证项记录命令、范围、退出结果和验证版本；历史错误与本次新增错误分开。未配置、无法运行或未授权的检查记录缺口，不伪造通过。
- 连续三轮核心问题未解决时停止重复同一路径，重新核对需求、事实源和失败证据，报告阻塞与下一步；不无限重试或扩大范围。

## 交付门禁

按需模式只核对本任务所需工作及实际参与者，不输出 22 行“不适用”。简单任务可报告“主 Agent 实施与自检”；需要独立审查时须有真实回执。全量模式另外核对 [全量交付门禁](../t-page-max/orchestration.md#全量交付门禁)。必需工作未执行、存在阻塞、适用规范未通过或最终验证未完成时，不能宣称代码可交付。

最简代码复核在交付前由主 Agent 按最终 diff 执行：逐文件核对本次新增代码中可删的冗余已删除，无需求外新增文件、抽象、依赖、注释和防御，并按 [新增功能边界](anchors.md#新增功能边界) 确认未擅自删改存量。判定标准用 [t-workflow#复杂度预算与最简代码](../t-workflow/SKILL.md#复杂度预算与最简代码必守) 的删减自检清单。角色审查通过不代替删减复核，各角色也不得扩大需求。

最终输出：

1. 已实现内容或只读审查结论，以及实际修改文件。
2. 实际执行者及结果：主 Agent 或所派角色、真实实例、范围和简短证据；全量模式附完整角色清单，同角色返工记录最新结论。
3. import、公共表格 Hook、现成能力复用三项必检结果，以及规范/文案审查、代码终审和运行验证结果。
4. 最简代码复核结论：已删除项与保留理由；存在更简单方案能同样满足需求时不得交付。
5. 未运行检查、待确认事实、接受的偏离及范围外发现。可以交付未完成状态说明或只读报告，不能把它们写成“全部通过”。

清理本次临时接口 dump 等取证产物，不生成无关追踪文件。回执和阶段清单默认留在对话中。单入口的调用不授权 Git 提交、推送或发布。

维护本调度约定时，用 [行为测试场景](../../tests/t-page-orchestration.md) 验证实际决策，不以匹配文档关键词代替测试。
