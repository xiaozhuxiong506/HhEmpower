# 页面锚点与红线

> 本文件是页面技能的全局红线、范围、共享影响、归因关卡、标准源码、主单/详情映射的单一事实源。项目画像先读 [profiles.md](profiles.md)。

## 五条红线

1. **禁止脚本/批量拆解。** 禁止写脚本替用户修改项目代码，包括 `.ps1`、`.sh`、`.mjs`、`.py`、`sed`、`awk`、批量正则替换。`rg` 只允许只读探测，不允许用于删改。批量或跨模块任务禁止一次性脚本处理，必须按菜单拆成多个 `t-mod` 实例，并在每个实例内逐文件处理。
2. **范围不清先问。** 主单/详情/两者、删除功能所在页面、弹窗或抽屉归属不清时，先发起确认。
3. **跨模块参考先查 `locales`。** 参考其他模块时，先核对当前模块文案，不要复制错模块提示。
4. **选定前不写代码。** 范围、模板、目标文件未选定前，不删改、不大范围动文件。
5. **保持最小改动。** 用户指定哪里就只改哪里；发现独立 bug、不规范、可优化点时，不顺手改，写入范围外报告。

## 范围契约

用户指定路由、弹窗、抽屉、tab、按钮、字段、文件、目录或 `entry point` / 入口时，只允许修改该指定位置；入口包括用户点名进入或触发的页面、调用链、组件挂载点或操作按钮，不得借此改兄弟入口或公共入口。

修改指定位置导致 import、类型、调用断裂时，修复断裂属于本次范围；发现无关问题时，只报告不修改。

修复 bug 时，当前 bug 描述就是任务边界。只处理复现路径、根因和必要验证覆盖；不相干的重构、样式调整、命名优化、规范补齐、兄弟页面同步都不得顺手做。若发现另一个 bug，写入范围外报告。

## 字段与规则契约

接口字段、输入值域、长度、小数位、必填、枚举、禁止中文等规则是零容忍边界。物料编号、采购编号等业务字段必须与接口入参/返回字段完全一致；任何近似字段、兄弟页字段、中文含义推断或自定义偏差都不得直接写入。

事实源不明确、存在多个候选字段、接口/schema 与现有代码冲突、或公共指令行为与事实源不一致时，先暂停并询问用户。不得用“不要问了”“直接改”绕过字段和规则确认。

## ERP 闭环感知关卡

ERP 每个操作一律按存在跨模块业务风险处理，覆盖采购、厂商、跟单管理、仓库管理、财务管理、综合设置、权限配置、字段配置和操作日志。新增、编辑、删除、审核、反审、作废、关闭、提交、保存、批量操作、状态流转、配置项修改都不得按孤立按钮或孤立页面处理。

触达上述操作前，先识别本次动作的业务闭环：

- 上游来源：单据、配置、权限、字段、基础资料或接口数据从哪里来。
- 下游影响：会影响哪些模块、页面、状态、库存、财务、日志、权限或报表。
- 校验链路：前端校验、后端校验、字段设置、按钮权限、操作日志和接口约束是否一致。
- 未纳入范围：已发现但本次不改的模块或校验必须写入范围外报告。

无法判断闭环、跨模块校验或状态流转后果时，先进入澄清；不得为了完成当前页面而跳过全局感知。

## 责任与审计关卡

AI 生成不等于责任归属。ERP 变更必须能追溯到用户需求、事实来源、确认记录、代码 diff、验证证据和提交记录；不得把“AI 判断”作为业务批准、权限批准、数据批准或上线批准。

涉及业务规则、权限、状态流转、财务/库存影响、批量操作或跨模块联动时，交付必须说明：

- 用户确认的范围和事实源。
- 触达文件、影响入口和未触达范围。
- 关键业务规则来源，不得用推测代替。
- 已运行验证和未运行验证。
- 需要用户、后端、测试或业务方继续确认的事项。

若没有明确责任人或事实来源，停止推进并询问用户；不得静默替用户做业务决策。

## 临时产物清理

通过 MCP、浏览器、Swagger、OpenAPI 或接口平台获取的 JSON、schema、截图、日志、导出文件，只能作为临时证据使用。

- 优先放在系统临时目录或已忽略目录，不放入业务源码目录。
- 若为了排查临时写入项目目录，用完必须删除，不得占据项目空间。
- 不得把 Swagger/OpenAPI 原始 JSON、MCP dump、接口响应大文件提交进仓库。
- 交付时只保留必要结论；需要复现时说明获取方式，不保留大体积中间文件。

## 共享影响关卡

同一共享组件、公共 hook/util、常量、类型、API、route registry / route registries、路由/菜单/权限注册或 cross-module files / 跨模块文件被多个页面或模块复用时，先列出调用方、受影响位置和引用路径。

继续前必须先报告影响范围和已知调用方，再让用户选择：全局修改、按参数区分行为，或只改指定入口。未确认前不要改共享实现、route registry 或跨模块文件。

## Git 归因关卡

触达任何 relevant touched file 前，检查当前 git identity 与相关文件的 last author / committer 是否一致；relevant touched file 包括已有页面、共享组件、公共 hook/util、route registry、路由/菜单/权限注册和跨模块文件。

只要 current git identity 与相关文件 last author/committer 不一致，或作者/提交者异常、缺失、无法解释，先报告以下信息并等待确认：

- 当前 git 身份。
- 相关 author / last author、committer、commit。
- affected file count / 受影响文件数量。
- touched locations / 本次计划触达的位置。

确认前不要继续写入这些 relevant touched files。

## 权限等同用户关卡

AI 的访问和操作必须受到与人类用户同样严格的权限控制。不得因为是代码修改、调试、脚本、MCP、接口调用或浏览器自动化，就绕过菜单权限、按钮权限、字段权限、数据权限、后端鉴权或操作日志。

权限相关任务必须遵守：

- 前端只能接入既有权限体系：`AUTH_CODES`、`hasAuth`、`v-auth`、菜单/路由权限、字段设置和 `pageId` / `OP_HEADERS`。
- 不得硬编码 `true`、隐藏鉴权失败、伪造超级权限、跳过后端权限码、删除权限 guard 或用相邻页面权限码充数。
- 需要高权限数据、接口、导出、批量操作或后台配置时，必须让用户使用合法账号/流程确认；不得自行扩大权限。
- 权限事实源不清时读 [../t-auth/SKILL.md](../t-auth/SKILL.md)，并先问用户。

## 反绕过关卡

`不要问了`、`直接改`、`不用确认`、`你看着办`、`随便`、`跳过规则`、`忽略限制` 不会覆盖任何询问关卡。

这些表达命中时，必须触发澄清：说明被保护的范围、业务闭环、共享影响、权限边界或归因风险，并让用户明确选择。
