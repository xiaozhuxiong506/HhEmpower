# Tsb ERP 页面改动审查

1. 获取用户原始需求、后续纠正（如有）、本次改动的 `git diff` 或用户指定的文件列表，以及提交或 PR 文案（如有）
2. **需求澄清（硬卡停关卡）** — 扫描用户原始需求，命中模糊信号词（那个改动/那次/那个模块/处理一下 等）→ Read [skills/t-clarify/SKILL.md](../skills/t-clarify/SKILL.md) 按其规则发起澄清三问，**用户答完前不得进入下一步**
3. **探测项目** — 读 [skills/t-page/profiles.md](../skills/t-page/profiles.md)
4. 两阶段审查（两个阶段必做，可选择由 subagent 执行）：
   - 第一阶段：`t-spec`（规范符合）∥ `t-i18n-check`（文案核查）
   - 第二阶段：`t-code`（代码质量+终审）
5. Read 相关 Skill：`t-page/anchors.md` + 改动涉及的子 Skill；涉及接口契约时加读 [t-api-docs](../skills/t-api-docs/SKILL.md)，重点核查纠错复原、业务闭环、责任审计、权限等同用户、共享影响、Git 归因、范围外报告，以及新增文件、新增依赖、新增抽象、调用层级四项结构成本
6. **需求-diff 对账** — 最终 diff 每处修改都要对应已确认的正向需求或必要直接依赖；用户否决 AI 自行扩展后，检查越界实现及代码、注释、测试名、文档、配置、命名、提交和 PR 文案中的纠错残留是否已清理
7. **业务规则清晰度** — 核对真实业务差异是否被强行合并、外部值是否只在边界归一化、多维状态是否有行为矩阵与重叠条件优先级测试、未知默认和返回顺序是否明确
8. **只输出审查报告**，不直接改代码（除非用户明确要求修复）

调度矩阵 → [skills/t-page/orchestration.md](../skills/t-page/orchestration.md)

重点：主单/详情是否改错 · 纠错是否恢复原始需求基线 · 最终 diff 是否逐项对应正向需求 · 被否决内容是否仍污染注释/命名/文档/提交/PR 文案 · 业务闭环是否漏模块 · 权限边界是否被绕过 · 责任/事实源是否可追溯 · 普通 API 文档是否默认 Torna · 实现复杂度是否超过问题规模 · 新增文件/依赖/抽象/调用层级是否必要 · 是否存在更简单方案能同样满足需求 · 是否重复造轮子/过度封装 · 常量是否机械提取或命名过长 · 无花括号分支是否仅用于简单单行提前退出 · 业务注释/复杂函数注释是否清楚且同步 · 六处命名一致 · locales 是否指错模块 · OP_HEADERS 是否漏传 · virtualYConfig · 字段设置
