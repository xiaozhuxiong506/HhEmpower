# Tsb ERP 页面改动审查

读取 [t-page](../skills/t-page/SKILL.md) 和 [调度约定](../skills/t-page/orchestration.md)，使用只读分析/审查权限。默认按需；同一任务已选择 [t-page-max](../skills/t-page-max/SKILL.md) 时保留全量模式。实际参与的实现角色转为核查，不改代码、不创建骨架或登记内容。

1. 获取用户原始需求及已确认范围、后续纠正、本次 git diff 或指定文件，以及已有的提交和 PR 文案。仅澄清影响审查范围的剩余歧义。
2. 必读 [t-standards](../skills/t-standards/SKILL.md) 及其 [reference.md](../skills/t-standards/reference.md)，继承 [anchors.md](../skills/t-page/anchors.md)，再按实际内容读取专业 Skill。涉及接口契约时读 [t-api-docs](../skills/t-api-docs/SKILL.md)，普通接口文档默认 Torna，用户明确指定时才用 Swagger/OpenAPI。
3. 主 Agent 按当前模式确定参与者并取证标准来源。简单局部任务直接核查，不派无关角色；复杂任务按职责派发，全量任务保留全部角色，不访问无关外部服务。
4. 非简单任务的两个阶段必做：第一阶段由 `t-spec` 审查规范，涉及文案时加 `t-i18n-check`，全量模式始终保留文案核查；第二阶段由 `t-code` 终审，之后交 `t-build` 验证。发现问题继续收齐报告，不进入自动返工；用户限制或环境使检查无法运行时如实标注。
5. 输出实际问题、文件位置、证据、影响及最小修正建议，附实际参与者、三项必检结果和未运行项。报告完成不等于规范通过或代码可交付。

重点核查：

- 需求-diff 对账：每处改动是否对应已确认的正向需求或必要直接依赖；纠错是否恢复需求基线，代码、注释、命名、文档、提交和 PR 文案中的越界实现及纠错残留是否清理。
- import 是否符合当前标准；公共表格 Hook 是否真正接通恢复、保存及事件；是否复用现成能力。
- 实现复杂度是否匹配问题规模，新增文件、依赖、抽象、调用层级是否必要；是否存在同样满足需求的更简单方案；常量、语法与注释是否适度、清晰。
- 业务规则清晰度：真实业务差异是否保留，外部值是否只在现有边界归一化，多状态逻辑是否有行为矩阵核对优先级、默认行为与返回顺序。
- 主单/详情、命名、字段、Tab、路由、权限、日志、文案、业务闭环和事实源是否完整。
- 最终版本是否完成当前模式要求的自检或独立审查与实际验证；适用规范的 Warning 不作为自动放行理由。

只有用户另行要求修复，才切换到开发/修复模式。
