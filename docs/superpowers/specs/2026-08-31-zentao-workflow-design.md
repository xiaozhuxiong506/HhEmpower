# 禅道单会话采集、开发分析、排期与解决闭环设计

## 目标

重构 `t-browser-mcp` 与 `t-zentao` 的禅道操作链路，使一次用户请求只建立一个禅道登录会话，先完整采集并区分【禅道需求】与【禅道Bug】，再按系统和代码模块分析、输出开发者可直接阅读的规范化方案。用户要求排期时，只对任务执行批量排期；开发完成后先给结论，再询问是否解决准确列出的 Bug 工单。

本设计中的【禅道需求】等同于禅道“指派给我的任务”；【禅道Bug】等同于禅道“指派给我的 Bug”。

## 当前问题

- 对外 MCP 仍只暴露 `zentao_collect_assigned_tasks`，虽然采集器已有任务与 Bug 使用同一 context 的雏形，但未进入真实工具链。
- 每次工具调用都会重新启动持久化 Chrome context；并发调用可能争用同一 Profile、弹出多个登录窗口或重复等待登录。
- 当前数据没有稳定输出所属项目、所属产品、系统、创建者、当前处理人、截止日期和工作项状态。
- 当前 Markdown 只按业务关键词分组，没有代码位置、共享组件影响和可执行处理方案。
- 当前没有标准化的批量排期与 Bug 解决能力。

## 范围

### 包含

- 单进程、单 Profile 的禅道会话复用与并发 single-flight。
- 一次采集任务和 Bug，并将列表条数优先设置为 `2000`。
- 提取列表与详情中的开发所需事实字段。
- TSBERP/HALLERP 系统识别、代码模块定位和共享组件影响分析。
- 规范化分析表、排期执行表、完成结论表。
- 任务批量排期和 Bug 工单解决操作。
- 兼容保留旧任务采集工具。

### 不包含

- 不保存禅道用户名、密码、Cookie 或验证码。
- 不把任务标题推断当作业务批准、权限批准或共享组件修改范围批准。
- 不在共享组件影响范围明确前修改代码。
- 不接入尚未验证的禅道内部 HTTP API；本次沿用可见页面与持久化浏览器 Profile。

## 总体操作链路

1. 主 Agent 调用统一采集工具一次。
2. MCP 取得或创建唯一禅道会话；发现未登录时只展示一个登录窗口，所有并发调用等待同一个登录结果。
3. 登录成功后依次采集“指派给我的任务”和“指派给我的 Bug”，两张列表都先尝试设置 `pageSize=2000`。
4. 统一工作项按场景、所属项目、所属产品和系统归一化。
5. 主 Agent 提醒用户当前 Git 分支，并在目标仓库中只读定位路由、页面、组件、API、权限、字段和日志关系。
6. 按“系统 -> 业务模块”聚合，相同模块的不同工单连续展示。
7. 检测到共享组件跨模块消费时，先向用户确认修改范围；确认前不派发实现。
8. 用户批准实现后，按模块执行、验证并汇总工单级结论。
9. 用户要求排期且已给出模块日期或具体日期后，直接进行任务批量编辑并返回执行结果；信息不足时只询问缺失的排期信息。
10. 所有开发结论输出后，列出可解决 Bug 并询问用户；用户回答后按准确 Bug 集合直接执行“解决”，不再增加第二轮确认。

## 单登录与并发模型

新增进程内禅道会话管理器，按规范化后的 `profileDir + browserChannel + headless` 作为会话键。

- 同一会话键只允许存在一个持久化 context。
- context 创建、登录等待、采集和写操作使用同一串行队列。
- 同一时刻到达的相同采集请求共享一个 in-flight Promise；后续调用等待现有采集，不再启动浏览器。
- 主 Agent 只负责一次采集。模块执行 Agent 只接收采集结果，不允许再次调用登录或采集工具。
- context 被用户关闭、浏览器崩溃或页面判定会话失效时，管理器清除失效句柄；下一次调用最多重新打开一个登录窗口。
- `keepBrowserOpen=true` 时保留 context 供后续排期/解决复用；`false` 时在当前请求完成后安全释放。
- 旧 `zentao_collect_assigned_tasks` 也走同一会话管理器，避免兼容入口重新引入重复登录。

## 统一工作项数据模型

```json
{
  "kind": "task",
  "scene": "禅道需求",
  "id": "9328",
  "url": "http://hallzd.internal.tsb.com/zentao/task-view-9328.html",
  "title": "订单出库-打印/导出资料",
  "project": "TSBERP1.0",
  "product": "TSBERP1.0",
  "system": "贸易系统",
  "creator": "林彦林",
  "assignee": "当前处理人",
  "deadline": "2026-09-02",
  "status": "未开始",
  "priority": "3",
  "severity": "",
  "content": "原始内容",
  "remarks": "原始备注",
  "description": "原始描述",
  "businessModule": "库存仓储模块",
  "moduleEvidence": "标题、描述、路由或仓库定位依据"
}
```

`kind` 只能是 `task` 或 `bug`；其展示场景固定为：

| kind | 场景 |
|---|---|
| `task` | 禅道需求 |
| `bug` | 禅道Bug |

系统根据“所属产品”和“所属项目”精确映射：

| 项目/产品名称规则 | 系统 |
|---|---|
| 以 `TSBERP` 开头 | 贸易系统 |
| 以 `HALLERP` 开头 | 展厅系统 |
| 其他或缺失 | 待确认 |

优先使用所属产品，其次使用所属项目；两者都存在且映射结果冲突时标为“待确认”。无法识别时必须保留原值，不得按标题猜系统。

## 代码定位与当前分支提醒

采集完成后、派发实现前，主 Agent 对每个工作项执行只读仓库分析：

1. 从标题、描述和备注定位菜单、路由、页面、弹窗/抽屉、API、权限码、字段设置和操作日志。
2. 记录业务模块和模块依据；依据不足时标记“待确认”。
3. 输出最小相关代码位置，格式为 `仓库绝对路径:行号`；不能只写目录或泛化模块名。
4. 检查相关组件的所有引用者。若同一组件被多个业务模块消费，记录共享模块清单并触发共享影响关卡。
5. 开始分析时只提醒一次当前 Git 分支，标准格式为 `当前开发分支：<branch>`。
6. 不固定输出仓库路径、HEAD、工作区状态或文件级 Git 最近修改者。
7. 没有定位到文件时，代码位置写“待定位”，不能编造。

## 规范化输出合同

### 1. 采集摘要

```markdown
## 禅道工作项摘要

| 场景 | 贸易系统 | 展厅系统 | 待确认 | 合计 |
|---|---:|---:|---:|---:|
| 禅道需求 | 0 | 0 | 0 | 0 |
| 禅道Bug | 0 | 0 | 0 | 0 |
```

### 2. 开发分析表

开发分析表前只输出一行当前分支提醒：

```text
当前开发分支：main
```

按“系统 -> 业务模块”建立标题；相同模块的工单放在同一张表中。列顺序固定，最后一列必须是可执行的“详细处理方案与对应位置”。

| 场景 | 所属项目 | 所属产品 | ID/链接 | 标题 | 创建者 | 当前处理人 | 截止日期 | 代码模块 | 共享影响 | 待确认项 | 详细处理方案与对应位置 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 禅道Bug | TSBERP1.0 | TSBERP1.0 | [9328](URL) | 标题 | 林彦林 | 未指派 | 未设置 | 库存仓储 | A、B 共用组件 | 修改范围待确认 | 1. 修改 `文件:行号`；2. 调整规则；3. 补充验证 |

“详细处理方案与对应位置”必须包含：

1. 问题或需求的代码落点。
2. 计划修改的行为，不写空泛的“按需求修改”。
3. 关联模块、共享组件和可能受影响的调用方。
4. 对应的验证方式。
5. 尚未确认的信息用“待确认”明确占位。

### 3. 共享组件确认表

当 A、B 两个或更多模块消费同一组件时，输出：

| 共享组件 | 代码位置 | 消费模块 | 涉及工单 | 必须确认的问题 |
|---|---|---|---|---|
| `SharedTable` | `绝对路径:行号` | A、B | #100、#101 | 全部模块都改，还是只改指定模块？ |

随后使用单选询问：全部涉及模块都修改、只修改某一模块、返回补充范围。用户确认前不得改代码。

### 4. 排期执行表

排期只接受 `kind=task` 的工作项。Bug 即使与任务同模块也不得混入。

| 业务模块 | 任务ID | 标题 | 计划截止日期 | 状态 | 预计 | 工时（消耗） | 剩余 | 批量编辑组 |
|---|---|---|---|---|---:|---:|---:|---|
| 采购模块 | #100 | 标题 | 2026-09-02 | 进行中 | 1h | 1h | 1h | 采购-2026-09-02-1h |

- 相同模块的多个任务默认使用相同截止日期。
- “后天、大后天”等相对日期按北京时间转换为绝对日期并在执行表中展示。
- 简单任务建议 `1h`，涉及共享组件、跨页面闭环或多处联动的任务建议 `2h`。
- 最终使用的每项时长必须在执行表中逐项出现；Agent 不得静默改变用户给出的日期或时长。
- 用户已经给出模块日期或具体日期时直接写入，不再追加“是否确认写入”的二次询问。

### 5. 开发完成结论表

| 场景 | ID | 系统/模块 | 完成结论 | 实际修改位置 | 验证结果 | 阻塞或遗留 | 建议解决 |
|---|---|---|---|---|---|---|---|
| 禅道Bug | #9328 | 贸易系统/库存仓储 | 已修复 | `绝对路径:行号` | 目标测试通过 | 无 | 是 |

只有 `kind=bug`、`completed=true` 且 `verified=true` 的工单才可建议解决。完成表之后单独列出准确 Bug ID，并询问用户是否解决；“全部解决”和“选择部分解决”必须明确区分。

## 共享影响硬卡点

以下任一条件成立即停止实现并询问用户：

- 同一组件被两个或更多业务模块引用。
- 同一路由或弹窗同时承担贸易系统与展厅系统入口。
- 修改公共工具会改变未列入工单的页面行为。
- 无法确定需求只针对 A 模块还是同时针对 A、B 模块。

问题必须给出已发现的组件、文件、消费模块和涉及工单，并提供互斥选项。不得用“默认全部修改”“保持兼容”绕过确认。

## 排期写入流程

新增任务排期工具，收到完整排期指令后直接执行：

1. 校验所有 ID 均来自本次采集且 `kind=task`。
2. 进入任务列表并将每页条数调整为 `2000`。
3. 按排期执行表精确勾选左侧复选框；验证选中 ID 集合与请求完全一致。
4. 点击左下角“编辑”进入批量编辑。
5. 对每个任务设置状态“进行中”、截止日期、预计、工时（消耗）、剩余。
6. 保存并重新读取任务详情，验证写入结果。
7. 任一 ID 缺失、选中集合不一致、字段无法定位或页面结构变化时停止，不部分提交。

建议 MCP 输入采用按模块分组的结构：

```json
{
  "groups": [
    {
      "module": "采购模块",
      "deadline": "2026-09-02",
      "tasks": [
        { "id": "100", "hours": 1 },
        { "id": "101", "hours": 2 }
      ]
    }
  ]
}
```

用户只说“帮我排期”但未给出各模块日期时，Agent 先按模块询问日期；用户给出日期后直接调用工具。

## Bug 工单解决流程

解决工具在用户回答解决范围后直接执行：

- 输入 ID 必须来自开发完成结论表，且场景必须是【禅道Bug】。
- 默认仅接受完成且验证通过的 Bug。
- 打开 Bug 后点击“解决”，只把“解决版本”选择为“主干”，把“解决日期”设置为执行时刻前 `30` 分钟。
- 解决时间以 `Asia/Shanghai` 计算，并按页面控件要求写入；除“解决版本”和“解决日期”外，其他字段保持页面原值，不主动填写或覆盖。
- 用户回答“全部解决”时，将本次完成结论表中建议解决的集合解析为准确 Bug ID；用户也可以只指定部分 ID。
- 执行后重新读取状态并报告成功、失败和未处理项，成功状态应为“已解决”而不是“已关闭”。

## MCP 工具设计

### 新增或正式暴露

- `zentao_collect_assigned_work_items`：单会话采集任务和 Bug。
- `zentao_analyze_work_items`：对已有统一工作项 JSON 做纯数据分析。
- `zentao_schedule_tasks`：任务批量排期并验证结果。
- `zentao_resolve_bugs`：按用户指定的准确 Bug 集合执行解决并验证结果。

### 保留兼容

- `zentao_collect_assigned_tasks`
- `zentao_analyze_tasks`

旧工具内部改为使用同一会话管理器，但返回结构保持兼容。

## 技能与命令职责

`t-zentao` 负责：

- 路由到统一采集工具。
- 确保主 Agent 只采集一次，模块 Agent 不再登录。
- 明确场景、系统、模块、代码分析步骤和当前分支提醒。
- 强制输出合同、共享组件确认、排期执行和 Bug 解决结果。
- 要求实现工作进入 `t-page` 并继承现有 ERP 业务闭环与权限关卡。

`t-zentao-collect` 命令负责：

- 使用默认 `pageSize=2000`、`maxTasks=2000`、`maxBugs=2000`。
- 选择统一工作项工具，而不是旧任务工具。
- 输出结构化摘要和开发分析表，不直接派发尚未确认的共享改动。

MCP 负责事实采集与页面操作，不负责共享代码修改范围的业务批准。

## 错误与安全边界

- 登录未完成：返回“请在已打开的唯一浏览器中登录”，不得创建第二个登录窗口。
- 任务或 Bug 其中一类采集失败：保留另一类结果并按场景返回错误。
- 产品未知、模块不清楚、文件未定位：保留事实并标记“待确认/待定位”。
- 页面批量编辑结构不符合预期：停止，不保存。
- 排期日期、ID 或时长发生变化时，以用户最后一次指令为准直接执行。
- 所有页面写操作都先解析为精确 ID 集合；“全部解决”仅代表本次完成结论表中建议解决的准确 Bug 集合。

## 验收标准

- 一次用户请求最多出现一个禅道登录窗口。
- 一次采集同时返回【禅道需求】和【禅道Bug】。
- 任务或 Bug 中可见的 ID、标题、所属项目、所属产品、创建者、截止日期能够进入统一模型；缺失值明确显示。
- TSBERP/HALLERP 映射准确，未知产品不猜测。
- 相同系统、相同模块的工单聚合展示。
- 每行方案包含代码位置、行为改动、关联影响和验证方式。
- 开发分析开始前提醒用户当前 Git 分支。
- 共享组件跨模块时用户确认前不实现。
- Bug 不进入排期；任务排期写入状态、截止日期、预计、工时（消耗）和剩余。
- 排期和 Bug 解决不追加二次确认，执行后返回逐项结果。
- 完成后输出工单级结论，再询问是否解决对应 Bug。
