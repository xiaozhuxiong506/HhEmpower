# 禅道单会话采集、开发分析与排期闭环设计

## 目标

重构 `t-browser-mcp` 与 `t-zentao` 的禅道操作链路，使一次用户请求只建立一个禅道登录会话，先完整采集并区分【禅道需求】与【禅道Bug】，再按系统和代码模块分析、输出开发者可直接阅读的规范化方案。用户要求排期时，只对任务执行批量排期；开发完成后先给结论，再询问是否关闭准确列出的工单。

本设计中的【禅道需求】等同于禅道“指派给我的任务”；【禅道Bug】等同于禅道“指派给我的 Bug”。

## 当前问题

- 对外 MCP 仍只暴露 `zentao_collect_assigned_tasks`，虽然采集器已有任务与 Bug 使用同一 context 的雏形，但未进入真实工具链。
- 每次工具调用都会重新启动持久化 Chrome context；并发调用可能争用同一 Profile、弹出多个登录窗口或重复等待登录。
- 当前数据没有稳定输出所属项目、所属产品、系统、创建者、当前处理人、截止日期和工作项状态。
- 当前 Markdown 只按业务关键词分组，没有仓库位置、共享组件影响、Git 证据和可执行处理方案。
- 当前没有受确认保护的批量排期与关闭能力。

## 范围

### 包含

- 单进程、单 Profile 的禅道会话复用与并发 single-flight。
- 一次采集任务和 Bug，并将列表条数优先设置为 `2000`。
- 提取列表与详情中的开发所需事实字段。
- TSBERP/HALLERP 系统识别、代码模块定位、共享组件影响分析和 Git 最近修改记录。
- 规范化分析表、排期预览表、完成结论表。
- 任务批量排期和工单关闭的显式确认关卡。
- 兼容保留旧任务采集工具。

### 不包含

- 不保存禅道用户名、密码、Cookie 或验证码。
- 不把任务标题推断当作业务批准、权限批准或共享组件修改范围批准。
- 不在用户确认前写入排期、关闭工单或修改代码。
- 不接入尚未验证的禅道内部 HTTP API；本次沿用可见页面与持久化浏览器 Profile。

## 总体操作链路

1. 主 Agent 调用统一采集工具一次。
2. MCP 取得或创建唯一禅道会话；发现未登录时只展示一个登录窗口，所有并发调用等待同一个登录结果。
3. 登录成功后依次采集“指派给我的任务”和“指派给我的 Bug”，两张列表都先尝试设置 `pageSize=2000`。
4. 统一工作项按场景、所属项目、所属产品和系统归一化。
5. 主 Agent 在目标仓库中只读定位路由、页面、组件、API、权限、字段和日志关系，并读取相关 Git 证据。
6. 按“系统 -> 业务模块”聚合，相同模块的不同工单连续展示。
7. 检测到共享组件跨模块消费时，先向用户确认修改范围；确认前不派发实现。
8. 用户批准实现后，按模块执行、验证并汇总工单级结论。
9. 用户要求排期时，先生成排期预览并确认，再进行任务批量编辑。
10. 所有开发结论输出后，列出可关闭工单并询问用户；明确确认后才关闭。

## 单登录与并发模型

新增进程内禅道会话管理器，按规范化后的 `profileDir + browserChannel + headless` 作为会话键。

- 同一会话键只允许存在一个持久化 context。
- context 创建、登录等待、采集和写操作使用同一串行队列。
- 同一时刻到达的相同采集请求共享一个 in-flight Promise；后续调用等待现有采集，不再启动浏览器。
- 主 Agent 只负责一次采集。模块执行 Agent 只接收采集结果，不允许再次调用登录或采集工具。
- context 被用户关闭、浏览器崩溃或页面判定会话失效时，管理器清除失效句柄；下一次调用最多重新打开一个登录窗口。
- `keepBrowserOpen=true` 时保留 context 供后续排期/关闭复用；`false` 时在当前请求完成后安全释放。
- 旧 `zentao_collect_assigned_tasks` 也走同一会话管理器，避免兼容入口重新引入重复登录。

## 统一工作项数据模型

```json
{
  "kind": "task",
  "scene": "禅道需求",
  "id": "9328",
  "url": "http://hallzd.internal.tsb.com/zentao/task-view-9328.html",
  "title": "订单出库-打印/导出资料",
  "project": "TSBERP1.0",
  "product": "TSBERP1.0",
  "system": "贸易系统",
  "creator": "林彦林",
  "assignee": "当前处理人",
  "deadline": "2026-09-02",
  "status": "未开始",
  "priority": "3",
  "severity": "",
  "content": "原始内容",
  "remarks": "原始备注",
  "description": "原始描述",
  "businessModule": "库存仓储模块",
  "moduleEvidence": "标题、描述、路由或仓库定位依据"
}
```

`kind` 只能是 `task` 或 `bug`；其展示场景固定为：

| kind | 场景 |
|---|---|
| `task` | 禅道需求 |
| `bug` | 禅道Bug |

系统根据“所属产品”和“所属项目”精确映射：

| 项目/产品名称规则 | 系统 |
|---|---|
| 以 `TSBERP` 开头 | 贸易系统 |
| 以 `HALLERP` 开头 | 展厅系统 |
| 其他或缺失 | 待确认 |

优先使用所属产品，其次使用所属项目；两者都存在且映射结果冲突时标为“待确认”。无法识别时必须保留原值，不得按标题猜系统。

## 仓库与 Git 分析合同

采集完成后、派发实现前，主 Agent 对每个工作项执行只读仓库分析：

1. 从标题、描述和备注定位菜单、路由、页面、弹窗/抽屉、API、权限码、字段设置和操作日志。
2. 记录业务模块和模块依据；依据不足时标记“待确认”。
3. 输出最小相关代码位置，格式为 `仓库绝对路径:行号`；不能只写目录或泛化模块名。
4. 检查相关组件的所有引用者。若同一组件被多个业务模块消费，记录共享模块清单并触发共享影响关卡。
5. 对每个相关文件读取最近一次已提交修改：作者、短提交哈希、提交日期和提交主题。
6. “Git 最近修改者”指相关文件最近一次已提交修改的作者，不等同于业务负责人或当前工单处理人。
7. 若相关文件存在本地未提交改动，只标记“工作区已有改动”；Git 无法证明其作者，不得猜测。
8. 没有定位到文件时，代码位置和 Git 字段均写“待定位”，不能编造。
9. 报告当前仓库、分支、HEAD 和相关文件工作区状态，避免开发者在错误仓库或错误分支上处理。

Git 证据的标准显示格式：

```text
张三 / a1b2c3d / 2026-08-20 / fix: 修复采购订单保存
```

多个文件存在不同作者时，以分号分隔并保留“文件 -> Git 证据”的对应关系。

## 规范化输出合同

### 1. 采集摘要

```markdown
## 禅道工作项摘要

| 场景 | 贸易系统 | 展厅系统 | 待确认 | 合计 |
|---|---:|---:|---:|---:|
| 禅道需求 | 0 | 0 | 0 | 0 |
| 禅道Bug | 0 | 0 | 0 | 0 |
```

### 2. 开发分析表

开发分析表前必须先输出仓库上下文：

| 代码仓库 | 当前分支 | HEAD | 相关工作区改动 | 相关文件 Git 最近修改者 |
|---|---|---|---|---|
| `仓库绝对路径` | `main` | `a1b2c3d / 提交主题` | `文件:状态` 或“无” | `文件 -> 作者/提交/日期/主题` |

按“系统 -> 业务模块”建立标题；相同模块的工单放在同一张表中。列顺序固定，最后一列必须是可执行的“详细处理方案与对应位置”。

| 场景 | 所属项目 | 所属产品 | ID/链接 | 标题 | 创建者 | 当前处理人 | 截止日期 | 代码模块 | Git 最近修改者 | 工作区状态 | 共享影响 | 待确认项 | 详细处理方案与对应位置 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 禅道Bug | TSBERP1.0 | TSBERP1.0 | [9328](URL) | 标题 | 林彦林 | 未指派 | 未设置 | 库存仓储 | `文件 -> 作者/提交/日期/主题` | 干净 | A、B 共用组件 | 修改范围待确认 | 1. 修改 `文件:行号`；2. 调整规则；3. 补充验证 |

“详细处理方案与对应位置”必须包含：

1. 问题或需求的代码落点。
2. 计划修改的行为，不写空泛的“按需求修改”。
3. 关联模块、共享组件和可能受影响的调用方。
4. 对应的验证方式。
5. 尚未确认的信息用“待确认”明确占位。

### 3. 共享组件确认表

当 A、B 两个或更多模块消费同一组件时，输出：

| 共享组件 | 代码位置 | 消费模块 | 涉及工单 | 必须确认的问题 |
|---|---|---|---|---|
| `SharedTable` | `绝对路径:行号` | A、B | #100、#101 | 全部模块都改，还是只改指定模块？ |

随后使用单选询问：全部涉及模块都修改、只修改某一模块、返回补充范围。用户确认前不得改代码。

### 4. 排期预览表

排期只接受 `kind=task` 的工作项。Bug 即使与任务同模块也不得混入。

| 业务模块 | 任务ID | 标题 | 计划截止日期 | 状态 | 预计 | 工时（消耗） | 剩余 | 批量编辑组 |
|---|---|---|---|---|---:|---:|---:|---|
| 采购模块 | #100 | 标题 | 2026-09-02 | 进行中 | 1h | 1h | 1h | 采购-2026-09-02-1h |

- 相同模块的多个任务默认使用相同截止日期。
- “后天、大后天”等相对日期按北京时间转换为绝对日期并在预览中展示。
- 简单任务建议 `1h`，涉及共享组件、跨页面闭环或多处联动的任务建议 `2h`。
- 最终使用的每项时长必须在预览中逐项出现；Agent 不得静默改变用户确认的日期或时长。
- 预览之后必须询问是否写入禅道。未确认只输出预览。

### 5. 开发完成结论表

| 场景 | ID | 系统/模块 | 完成结论 | 实际修改位置 | 验证结果 | 阻塞或遗留 | 建议关闭 |
|---|---|---|---|---|---|---|---|
| 禅道Bug | #9328 | 贸易系统/库存仓储 | 已修复 | `绝对路径:行号` | 目标测试通过 | 无 | 是 |

只有 `completed=true` 且 `verified=true` 的工单才可建议关闭。完成表之后单独列出准确 ID，并询问用户是否关闭；“全部关闭”和“选择部分关闭”必须明确区分。

## 共享影响硬卡点

以下任一条件成立即停止实现并询问用户：

- 同一组件被两个或更多业务模块引用。
- 同一路由或弹窗同时承担贸易系统与展厅系统入口。
- 修改公共工具会改变未列入工单的页面行为。
- 无法确定需求只针对 A 模块还是同时针对 A、B 模块。

问题必须给出已发现的组件、文件、消费模块和涉及工单，并提供互斥选项。不得用“默认全部修改”“保持兼容”绕过确认。

## 排期写入流程

新增任务排期工具，采用“预览”和“执行”两阶段：

1. 校验所有 ID 均来自本次采集且 `kind=task`。
2. 进入任务列表并将每页条数调整为 `2000`。
3. 按预览表精确勾选左侧复选框；验证选中 ID 集合与请求完全一致。
4. 点击左下角“编辑”进入批量编辑。
5. 对每个任务设置状态“进行中”、截止日期、预计、工时（消耗）、剩余。
6. 保存前返回最终页面预览与选中 ID；调用方必须取得用户的当次明确确认。
7. 用户确认后执行保存，并重新读取任务详情验证写入结果。
8. 任一 ID 缺失、选中集合不一致、字段无法定位或页面结构变化时停止，不部分提交。

建议 MCP 输入采用按模块分组的结构：

```json
{
  "mode": "preview",
  "groups": [
    {
      "module": "采购模块",
      "deadline": "2026-09-02",
      "tasks": [
        { "id": "100", "hours": 1 },
        { "id": "101", "hours": 2 }
      ]
    }
  ]
}
```

`mode=apply` 只允许在用户确认同一份预览后调用。

## 工单关闭流程

关闭工具同样采用“预览”和“执行”两阶段：

- 输入 ID 必须来自开发完成结论表。
- 默认仅接受完成且验证通过的工单。
- 预览返回场景、ID、标题、当前状态和将执行的动作。
- Bug 若需要先解决再关闭，工具不得替用户发明解决方案、解决版本或责任人；缺字段时返回阻塞并询问。
- `mode=apply` 前必须取得用户对准确 ID 集合的当次确认。
- 执行后重新读取状态并报告成功、失败和未处理项。

## MCP 工具设计

### 新增或正式暴露

- `zentao_collect_assigned_work_items`：单会话采集任务和 Bug。
- `zentao_analyze_work_items`：对已有统一工作项 JSON 做纯数据分析。
- `zentao_schedule_tasks`：任务排期预览/执行。
- `zentao_close_work_items`：工单关闭预览/执行。

### 保留兼容

- `zentao_collect_assigned_tasks`
- `zentao_analyze_tasks`

旧工具内部改为使用同一会话管理器，但返回结构保持兼容。

## 技能与命令职责

`t-zentao` 负责：

- 路由到统一采集工具。
- 确保主 Agent 只采集一次，模块 Agent 不再登录。
- 明确场景、系统、模块、仓库和 Git 分析步骤。
- 强制输出合同、共享组件确认、排期确认和关闭确认。
- 要求实现工作进入 `t-page` 并继承现有 ERP 业务闭环与权限关卡。

`t-zentao-collect` 命令负责：

- 使用默认 `pageSize=2000`、`maxTasks=2000`、`maxBugs=2000`。
- 选择统一工作项工具，而不是旧任务工具。
- 输出结构化摘要和开发分析表，不直接派发尚未确认的共享改动。

MCP 负责事实采集与受保护的页面操作，不负责业务批准、代码范围批准或关闭批准。

## 错误与安全边界

- 登录未完成：返回“请在已打开的唯一浏览器中登录”，不得创建第二个登录窗口。
- 任务或 Bug 其中一类采集失败：保留另一类结果并按场景返回错误。
- 产品未知、模块不清楚、文件未定位、Git 无记录：保留事实并标记“待确认/待定位”。
- 页面批量编辑结构不符合预期：停止，不保存。
- 用户修改了预览中的日期、ID 或时长：生成新预览并重新确认。
- 所有外部写操作均为精确 ID 集合，禁止“当前页全部”“查询结果全部”等开放范围写入。

## 验收标准

- 一次用户请求最多出现一个禅道登录窗口。
- 一次采集同时返回【禅道需求】和【禅道Bug】。
- 任务或 Bug 中可见的 ID、标题、所属项目、所属产品、创建者、截止日期能够进入统一模型；缺失值明确显示。
- TSBERP/HALLERP 映射准确，未知产品不猜测。
- 相同系统、相同模块的工单聚合展示。
- 每行方案包含代码位置、行为改动、关联影响和验证方式。
- Git 最近修改者有文件与提交证据，本地未提交改动不猜作者。
- 仓库路径、当前分支、HEAD 和相关工作区状态在分析结果中可见。
- 共享组件跨模块时用户确认前不实现。
- Bug 不进入排期；任务排期写入状态、截止日期、预计、工时（消耗）和剩余。
- 排期与关闭均有精确预览和当次确认，不发生开放范围写入。
- 完成后输出工单级结论，再询问是否关闭。
