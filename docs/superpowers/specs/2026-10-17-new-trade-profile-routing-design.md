# NewTrade 第三画像与规范分发设计

## 背景

HhEmpower 当前支持旧贸易系统与展厅系统。新项目 `Tsb.NewTradeErpPC` 同样使用 `ts*` 页面前缀，但拥有独立的项目规范、框架结构和实现约定。若继续使用页面前缀判断，会把旧贸易规则错误分发给新项目。

本次增加第三套项目画像。第三画像保持轻量，不把新项目根目录的技术规范复制到 HhEmpower，也不新建一套重复的专业 Skills。

## 目标

- 通过项目根目录 `package.json.name` 唯一确定当前项目画像。
- 新贸易任务优先读取目标项目根目录 `docs` 下的规范。
- 保留 HhEmpower 的需求、范围、责任、调度、审查与验证治理。
- 保持旧贸易系统和展厅系统现有技术规则不变。
- 阻止三套画像之间的组件、权限、日志、字段和路由规则串用。

## 非目标

- 不修改 `Tsb.NewTradeErpPC` 业务代码或项目文档。
- 不复制 `Tsb.NewTradeErpPC/docs` 到 HhEmpower。
- 不新增 `new-t-list`、`new-t-auth` 等平行 Skill 目录。
- 不根据仓库名、文件路径、页面前缀、组件、Hook、Git remote 或文档存在情况猜测画像。
- 不把展厅大屏 `dp*` 纳入本次三套页面画像。
- 不改变 `/t-page` 与 `/t-page-max` 的参与范围定义。

## 画像判定

主 Agent 从当前任务目标所属项目根目录读取 `package.json`，只使用顶层 `name` 字段判定画像。

| `package.json.name` | 画像 | 技术规范来源 |
| --- | --- | --- |
| `tsb-new-trade-erp-pc` | 新贸易 | 目标项目根目录 `docs` |
| `tsb-erp` | 旧贸易 | HhEmpower 现有旧贸易画像和专业 Skills |
| `tsb-hall-user` | 展厅 | HhEmpower 现有展厅画像和专业 Skills |

判定规则：

1. `package.json` 不存在、无法读取、`name` 缺失或不在表内时，画像为待确认。
2. 待确认状态只能继续只读核查或询问用户，不得回退到路径、前缀或实现特征进行猜测。
3. `src/views/ts*`、`src/views/th*` 和 `src/views/dp*` 仅可在画像确定后用于定位画像内部的页面范围，不参与画像选择。
4. 同一任务确定画像后，主 Agent 与所有子代理共用该画像。除非目标项目根发生变化，不得中途切换。
5. 多仓库任务按每个目标项目根分别判定，不用一个仓库的画像覆盖另一个仓库。

## 新贸易规范读取

命中 `tsb-new-trade-erp-pc` 后：

1. 页面开发、修改和审查开始前必须读取目标项目的 `docs/项目规范.md` 与 `docs/框架规范.md`。
2. 涉及操作日志、`OP_HEADERS`、`pageId`、打印或导出日志时，追加读取 `docs/操作日志规范.md`。
3. 文档路径以目标项目根为基准，不使用 HhEmpower 的绝对开发机路径。
4. 必需文档不存在、不可读或相互冲突时停止写入，报告缺失或冲突，不自动套用旧贸易或展厅实现。
5. 新贸易的组件、目录、路由、权限、日志、API、字段、i18n 和验证命令以目标项目文档及当前源码为准。

## 保留的跨项目治理

第三画像继续继承 HhEmpower 中与具体实现无关的治理规则：

- 产品文档先做前后端责任拆分并输出规范化前端需求分析。
- 需求歧义、范围歧义和事实来源缺口在写入前确认。
- 每一处最终 diff 对应已确认需求或必要直接依赖。
- 用户纠错时恢复正向需求基线，不留下反需求注释、命名或文档。
- 新增功能默认保留存量代码，未授权不重构、不删除、不清理旧注释。
- 批量同类改动先做一处样例，展示实际 diff 与验证结果，用户确认后再推广。
- 小功能采用最小充分实现，不增加无必要文件、依赖、抽象和调用层级。
- API、权限码、字段、`pageId` 和日志系统必须有明确事实来源。
- 共享组件修改先核对调用方和影响范围。
- 多 Agent 任务保持单一调度、唯一文件负责人和真实回执。
- 开发任务完成与风险相称的规范审查、代码审查和机器验证。
- Git 归因、用户已有未提交修改和只读边界继续受保护。

这些治理规则不能覆盖或重写新贸易项目文档中的具体技术约定。

## 专业 Skill 分发

`t-page` 仍按任务信号分发到现有专业 Skill。命中新贸易画像时，专业 Skill 只负责职责边界、事实核对和交付门禁；具体实现从目标项目文档和同项目源码读取。

| 任务范围 | 分发目标 | 新贸易处理方式 |
| --- | --- | --- |
| 列表、查询、表格、分页 | `t-list` | 读取项目文档中的列表页规范，不套旧贸易组件组合 |
| 权限码、按钮显隐 | `t-auth` | 读取项目文档和当前权限实现，不套跨路由权限假设 |
| 操作日志、`pageId` | `t-oplog` | 读取 `docs/操作日志规范.md`，继续执行真实系统与后台来源门禁 |
| 字段、表单、列字段对齐 | `t-field` | 使用项目文档定义的字段契约，不假设旧动态字段设置机制存在 |
| API 与类型 | `t-api-docs` | 区分项目实现契约与服务端接口事实，不从本地类型推断完整后端约束 |
| 弹窗、抽屉 | `t-dialog` | 使用项目文档中的容器和样式约定 |
| 详情页 | `t-detail` | 仅使用项目文档和新项目已有详情证据，不套旧详情模板 |
| 路由、菜单、Tab | `t-registry` | 使用项目文档和当前动态菜单实现 |
| 代码规范与复杂度 | `t-standards` | 保留最小改动治理，技术写法以项目文档为准 |

专业 Skill 不因支持第三画像而复制新项目规范正文。

## 旧贸易与展厅

- `tsb-erp` 继续使用旧贸易画像及其已有标准页、组件、权限、日志、字段和路由规则。
- `tsb-hall-user` 继续使用展厅画像及其已有标准页、组件、权限、日志、字段和路由规则。
- 两者不读取新贸易项目的 `docs`，也不继承新贸易的 `Ts*` 组件或集中式日志登记约定。
- 页面前缀只能在画像确定后定位页面；不能因为旧贸易和新贸易都使用 `ts*` 而共享实现规则。

## 失败与冲突处理

- 未命中已登记包名：输出实际读取到的 `package.json.name`，询问用户，不开始实现。
- 目标跨多个仓库：逐仓库判定画像，分别记录可写范围和规范来源。
- 新贸易项目文档与源码不一致：记录冲突位置，优先要求确认，不擅自选择其中一方。
- HhEmpower 通用治理与项目技术规范冲突：范围、权限、责任和用户授权边界继续有效；具体技术写法以项目文档为准。
- 用户已有修改与本次任务重叠：停止覆盖，先说明重叠文件与影响。

## 预计修改范围

实现阶段优先修改单一事实源和必要入口，不复制规则：

- `skills/t-page/profiles.md`
- `skills/t-page/SKILL.md`
- `skills/t-workflow/SKILL.md`
- `skills/t-standards/SKILL.md`
- `rules/t-agent-guidance.mdc`
- 与新贸易任务会直接误套旧实现的专业 Skills
- 对应策略测试和行为回归文档

具体专业 Skill 仅增加第三画像分流和文档优先门禁；若某 Skill 已完全从 `profiles.md` 读取项目差异，不重复修改。

## 验证设计

至少覆盖以下场景：

1. `tsb-new-trade-erp-pc` 命中新贸易，并要求读取两份核心文档。
2. 新贸易操作日志任务追加读取日志规范。
3. `tsb-erp` 继续命中旧贸易，不读取新贸易文档。
4. `tsb-hall-user` 继续命中展厅，不读取新贸易文档。
5. 未知包名、缺失包名和无法读取 `package.json` 时停止，不用 `ts*` 或 `th*` 猜测。
6. 即使出现 `TsListView`、`useVxePage` 或新贸易文档，也不能在包名未命中时选择新贸易。
7. 新贸易专业任务正确分发到现有 Skill，但不会应用旧贸易或展厅的具体组件和契约。
8. `/t-page` 与 `/t-page-max` 使用同一画像判定规则，差异仅在参与角色范围。

验证包含 Skill 格式检查、策略测试、链接检查、`git diff --check` 和项目现有完整测试。验证结论只证明 HhEmpower 分发规则，不冒充新贸易业务项目已完成端到端验证。

## 发布边界

设计文档、实现提交、GitHub 推送和 Marketplace 刷新是不同动作。实现完成并验证通过后，只有得到明确发布授权才执行导出、推送或 Marketplace 更新。现有未提交的 `t-auth` 修改和钉钉 Skills 不自动并入本次第三画像变更。
