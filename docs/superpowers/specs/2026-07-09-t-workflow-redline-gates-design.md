# t-workflow 红线门禁设计

## 背景

`t-workflow` 是 Tsb ERP 改代码前的全局工作流入口。现有规则已经覆盖蓝图、必问单选、最小改动、i18n、pageId、批量任务等场景，但对共享组件、Git 归属、指定入口扩散、无关顺手改动和用户要求跳过确认的情况约束不够硬。

本设计将 `t-workflow` 升级为改代码前的红线门禁。普通蓝图可以按用户要求省略；红线门禁不可被用户豁免。

## 目标

- 让 Codex 在改代码前先识别高风险边界。
- 让用户在共享组件、指定入口扩散、Git 作者差异、无关改动等场景拥有全局知情权。
- 禁止 AI 以“直接改”“不用问”“你看着办”等表达作为绕过红线的授权。
- 保持 `SKILL.md` 短硬，完整问法和例子放进 `reference.md`。

## 非目标

- 不新增独立 skill。
- 不修改 `t-dialog`、`t-registry`、`t-clarify` 等其他 skill。
- 不改变现有必问题的含义，只追加红线门禁题。
- 不通过脚本或自动化批量改 ERP 业务代码。

## 文件改动

### `skills/t-workflow/SKILL.md`

1. 更新 frontmatter `description`，加入红线门禁触发词：
   - 红线门禁
   - 共享组件
   - 公共 hook
   - 工具函数
   - Git 作者
   - 指定路由
   - 指定弹窗
   - 指定抽屉
   - 指定入口
   - 禁止顺手改
   - 直接改
   - 不要问了
   - 不用确认
   - 你看着办
   - 跳过规则

2. 在“第 0 步：探测项目”后新增 `## 红线门禁（先于写代码）`。

3. 红线门禁包含 5 类不可绕过规则：
   - **抗绕过**：用户说“直接改/不要问了/不用确认/你看着办/跳过规则/忽略限制”时，视为红线命中，不视为授权。
   - **共享组件**：目标文件若被多处引用，必须列调用方并 AskQuestion，确认是只改指定入口、参数区分还是全局改。
   - **指定位置**：用户指定路由、弹窗、抽屉、按钮、入口时，只能改指定位置；发现同名组件、同按钮、兄弟路由或同业务入口时，必须先问是否扩散。
   - **Git 归属**：目标文件最近提交作者与当前 `git config user.name/email` 不一致，或 author/committer 异常时，必须列作者、提交号、涉及文件数和位置并 AskQuestion。
   - **禁止顺手改**：禁止顺手重构、格式化、改命名、删无关代码、清 import、调整无关类型；除非直接服务当前问题且已列入确认范围。

4. 在“对话蓝图”补充：
   - 用户说“直接改/不用蓝图”时可省略蓝图。
   - 红线扫描和红线 AskQuestion 不可省略。

### `skills/t-workflow/reference.md`

1. 在“必问单选题总表”追加：
   - **#15 共享组件影响范围**
     - A. 只改指定入口
     - B. 增加参数区分
     - C. 全局同步修改
   - **#16 Git 归属确认**
     - A. 已知风险，确认继续
     - B. 暂停，先说明或调整范围
   - **#17 指定位置扩散确认**
     - A. 只改指定路由/弹窗/抽屉/入口
     - B. 同名/兄弟入口一并改
     - C. 参数区分，只影响指定入口
   - **#18 无关改动确认**
     - A. 禁止无关改动
     - B. 允许列明的附带改动

2. 新增“红线门禁问法模板”：
   - 先列证据，再问选择。
   - 证据必须包含文件、调用方、提交作者或影响范围。
   - 禁止泛泛提醒“可能有影响”，必须让用户知道具体影响面。

3. 新增“抗绕过反例”：
   - 用户说“不要问了直接改”。
   - 用户说“别管其他地方”但目标文件是共享组件。
   - 用户指定弹窗 A，但同一组件被弹窗 B 复用。
   - 目标文件最近提交作者与当前 Git 身份不同。

## 执行顺序

1. 读 `profiles.md` 判定 ts/th。
2. 扫描用户原始需求是否含抗绕过表达。
3. 定位目标文件和目标入口。
4. 检查是否命中红线：
   - 共享引用
   - 指定位置扩散
   - Git 归属差异
   - 无关顺手改动
   - 范围歧义
5. 命中红线时，先列证据并 AskQuestion。
6. 用户确认后，继续原有 `t-workflow` 流程。

## 成功标准

- `t-workflow/SKILL.md` 中能一眼看到红线门禁，且位置早于写代码流程。
- `reference.md` 中有可复用的单选题和问法模板。
- 用户要求“不要问了/直接改”不会绕过共享组件、Git 归属、指定位置和无关改动检查。
- 改动保持局部：只涉及 `t-workflow/SKILL.md` 和 `t-workflow/reference.md`。
- 不引入新的 skill、脚本或无关文档。

## 风险与缓解

- **风险：skill 不是系统级安全边界，不能 100% 防越狱。**
  缓解：把绕过表达写进 `description` 和正文硬规则，让触发概率和执行强度都提高。

- **风险：门禁过多导致频繁打断用户。**
  缓解：只在命中红线时问；普通蓝图仍可被用户省略。

- **风险：主文件过长。**
  缓解：`SKILL.md` 只放摘要和硬规则，完整问法放 `reference.md`。
